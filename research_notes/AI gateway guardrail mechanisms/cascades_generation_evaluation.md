# AI gateway guardrails: cascades and routing, LLM-generated validators in a sandbox, and evaluation

Research date: Friday, Oct 30, 2026. Scope: a local Node.js "University Hub" gateway that screens student → agent messages, agent replies and professor posts for PII (SSNs, card numbers), offensive language and harmful intent. Sources are dated where the source gives a date. Search snippets that could not be confirmed against the primary page are flagged.

## (a) Cascade and routing design: how to avoid running every check on every message

### Takeaway
Published cascade work agrees on one pattern: a cheap first stage handles most traffic, and an item goes to a more expensive stage only when the cheap stage is unsure (a confidence or entropy threshold). Two more things can replace "run every function every time": a router that picks which policies apply, and a single multi-label LLM call that returns every category verdict at once. Moderation-specific cost/accuracy numbers are scarce. Most of the figures come from general LLM cascade papers.

### Cited Findings
**Cascades and early exit**
- FrugalGPT (Chen, Zaharia, Zou; arXiv 2305.05176, 2023) is the standard reference for small-to-large LLM cascades. The search snippet reports "reduces cost by 80% while improving accuracy by 1.5% compared to GPT-4". I did not re-check this against the abstract, and the abstract's headline numbers may differ, so check the PDF before quoting it. — [FrugalGPT](https://arxiv.org/pdf/2305.05176)
- Online Cascade Learning (arXiv 2402.04513, 2024) builds a cascade of logistic regression → BERT-base → GPT-3.5 Turbo (Llama 2 70B as an alternative top model). It is benchmarked on a HateSpeech dataset, and the setting is framed as running "from customer feedback analysis to content moderation". The smaller models are trained online on the LLM's own labels, so over time the cheap stages answer more items themselves. — [Online Cascade Learning](https://arxiv.org/pdf/2402.04513)
- COEF-VQ (arXiv 2412.10435) moderates video, including inappropriate-content detection. It escalates to a multimodal LLM only when the base model's prediction **entropy** passes a threshold, and it uses the LLM stage mainly to **cut false positives**. The authors say it "maximizes detection accuracy while controlling computational costs". — [COEF-VQ](https://arxiv.org/pdf/2412.10435)
- Conformal Cascade (arXiv 2607.25018, 2026) gives accuracy guarantees for multi-tier LLM cascades that do not depend on the data distribution. In one setting, a looser acceptance rule cut expected cost from 2.86 to 1.34 (−53%) and lost 5.3 percentage points of accuracy. That is an explicit, tunable cost/accuracy trade. — [Conformal Cascade](https://arxiv.org/html/2607.25018v1)
- CascadeDebate (arXiv 2604.12262, 2026) adds multi-agent deliberation only at the escalation point. It matches or beats the large multi-agent baseline at 20–35% lower token cost. — [CascadeDebate](https://arxiv.org/abs/2604.12262)
- A critical position paper (arXiv 2409.03219, "Content Moderation by LLM: From Accuracy to Legitimacy") argues that the LLM's accuracy edge over traditional AI and human moderators "has been largely offset by its weakness in cost, especially on easy cases". That is an argument for sending only the hard cases to an LLM. — [ResearchGate copy](https://www.researchgate.net/publication/383792306_Content_Moderation_by_LLM_From_Accuracy_to_Legitimacy)
- AutoRelAnnotator (arXiv 2606.25871) uses calibrated model cascades for a different task, relevance labelling in sponsored search. It reports 89.1% accuracy with 50.1% cost savings in production. This is evidence for calibrated cascades in general, not for moderation. — [AutoRelAnnotator](https://arxiv.org/pdf/2606.25871)

**Semantic routing to choose checks or policies**
- semantic-router (Aurelio Labs) v1.x is rebuilt around **calibrated confidence**. Calling `fit()` with "a few dozen labelled example queries" makes "a confidence of 0.85 mean the route is right about 85% of the time", so a threshold can be set from a policy such as "only act when 90% sure". Labelled examples can use `None` for queries that should match no route. — [Aurelio docs, v1 migration](https://docs.aurelio.ai/docs/semantic-router/v1/user-guide/guides/migration-to-v1); [GitHub](https://github.com/aurelio-labs/semantic-router)
- v1 breaking change: there is "no threshold unless you set one, and the best route always wins, however weak the match". `score_threshold` was renamed `confidence_threshold`. Precedence is per-call over per-route over router-wide (`router.set_threshold(threshold=0.8, route_name=...)`, `router(query, threshold=0.6)`). Pin `semantic-router<1` to keep the old API. — [Aurelio docs, v1 migration](https://docs.aurelio.ai/docs/semantic-router/v1/user-guide/guides/migration-to-v1)
- Before v1, each encoder had its own default threshold, and the values differed a lot: the examples used 0.82 for OpenAI and 0.3 for Cohere. When no route scored above the threshold, the router returned `None`, which the application had to handle. — [GitHub discussion #61](https://github.com/aurelio-labs/semantic-router/discussions/61); [RouteLayer API](https://docs.aurelio.ai/semantic-router/_autosummary/semantic_router.layer.RouteLayer.html)
- The v1 docs list **guardrails** as a use case ("catch off-topic, unsafe or out-of-scope requests before they reach an LLM"). They include a "HybridRouter" guardrail example with `allowed`/`blocked` routes, plus a `Chain` that "tries a fast router first and only falls through to a slower one when the fast one isn't sure". The `Chain` is an early-exit cascade built into the router. — [Aurelio docs intro](https://docs.aurelio.ai/docs/semantic-router/v1/get-started/introduction)
- semantic-router is a Python library. I found no official Node.js port during this research (see Gaps).

**One LLM call, many category verdicts**
- Llama Guard 3 checks every category in one call. The first output line is `safe` or `unsafe`, and if unsafe, "a second line must include a comma-separated list of violated categories" (for example `unsafe\nS1,S2`). Categories: S1 Violent Crimes, S2 Non-Violent Crimes, S3 Sex Crimes, S4 Child Exploitation, S5 Defamation, S6 Specialized Advice, S7 Privacy, S8 IP, S9 Indiscriminate Weapons, S10 Hate, S11 Self-Harm, S12 Sexual Content, S13 Elections, and S14 Code Interpreter Abuse (8B text model only). The prompt assesses "ONLY THE LAST {{ role }}" (User or Agent), so one template covers both input and output screening. — [Meta Llama Guard 3 docs](https://www.llama.com/docs/model-cards-and-prompt-formats/llama-guard-3/)
- The original Llama Guard paper says the format "accommodates binary and multi-label classification", with a score read from the first token's probability. It also allows "1 vs. all classification" by putting one category in the prompt. So both "all categories in one call" and "one call per category" are supported. — [Llama Guard paper, arXiv 2312.06674](https://arxiv.org/html/2312.06674v1)
- Custom categories can be added to the category list in the prompt. — [moderationapi.com self-hosting guide](https://moderationapi.com/blog/how-to-self-host-use-llama-guard-3/)
- Caution: some third-party sites show Llama Guard returning JSON with their own category names. Those are wrappers. The model's real output is plain text. — [Meta docs](https://www.llama.com/docs/model-cards-and-prompt-formats/llama-guard-3/) vs. third-party pages such as [nocloudgpt](https://nocloudgpt.com/models/llama-guard-3/)
- OpenAI's moderation system (Markov et al., AAAI 2023) is likewise one model that returns several category flags at once (S, H, V, HR, SH, S3, H2, V2). — [AAAI paper](https://ojs.aaai.org/index.php/AAAI/article/view/26752); [eval dataset card](https://huggingface.co/datasets/mmathys/openai-moderation-api-evaluation)

### Inferences
- **Proposed pipeline for the Hub (my design, built from the patterns above, not taken from any one source):**
  1. **Stage 0, deterministic, always on, microseconds.** Generated validators run here. Each one has a cheap *trigger* (for example "a 9-digit run, with or without dashes" for SSN, or "13–19 digits with spaces or dashes" for cards) and runs its full validator only when the trigger fires. For cards that means the Luhn checksum plus issuer prefix; for SSNs it means rejecting invalid area/group/serial values. This is the "rule trigger/prefilter" idea: you never run all functions, only the ones whose trigger matched. Triggers are what keep false positives down. The user's complaint about Presidio fits this, but I found no source that measures Presidio's false-positive rate.
  2. **Stage 1, policy router.** An embedding or keyword router (semantic-router-style, with calibrated confidence) decides which policies are relevant, or that the message is clearly benign. It is direction-aware: student input, agent output and professor post carry different risks.
  3. **Stage 2, a single structured LLM call** (Llama Guard-style, multi-label) for items the router marks uncertain or risky. It returns all category verdicts in one JSON object, so you never make one call per check. The project already uses structured output with Haiku (CLAUDE.md, Part 4), so this fits the existing `callModel` path.
  4. Escalation thresholds are set per direction and per category from calibration data (see (c)). They are not guessed.
- The COEF-VQ result suggests a useful split of work: let the cheap deterministic stage be high-recall, and use the LLM stage mainly to *clear false positives*. That speaks directly to the Presidio complaint.
- Fail-safe rule: if the LLM stage fails, the gateway should not silently pass high-risk categories. This matches the project's "no hidden fallback" rule. It is my inference, not sourced.

### Gaps
- I found no published head-to-head numbers for a moderation cascade made of regex prefilter, embedding router and LLM (cost per 1k messages vs. recall). The cited numbers come from general cascades or video moderation.
- I found no official Node.js/JS port of semantic-router. A JS build would need its own embedding call plus cosine similarity, or a local model (for example transformers.js). Not verified.
- I did not confirm Presidio's false-positive behaviour from a primary benchmark. The user's experience is the only evidence.
- The FrugalGPT "80% / 1.5%" figure is from a search snippet. Check it against the paper.

## (b) LLM-generated deterministic validator code, and running it in a sandbox (workerd and alternatives)

### Takeaway
Research on LLM-generated detection rules (mostly Sigma and email rules) all ends up doing the same thing: score generated rules against held-out positive and negative examples, and add a judge/repair loop. Similarity scores such as BLEU are a weak substitute. For running the code, workerd gives capability-based isolation with no outbound network if you set `globalOutbound = null` and grant no bindings. Its own README says it is **not** a hardened sandbox for untrusted code without an outer VM/sandbox. In Node, `node:vm` is explicitly not a security boundary. `isolated-vm` is in maintenance mode, and QuickJS-in-WASM is the most self-contained in-process option, with known memory-limit gaps.

### Cited Findings
**LLM-generated detection rules: research and verification**
- "Evaluating LLM Generated Detection Rules in Cybersecurity" (Bertiger, Filar et al., Sublime Security; arXiv 2509.16749, submitted 20 Sep 2025, CAMLIS 2025) releases an open-source framework and benchmark that uses "a holdout set-based methodology" to compare LLM-generated rules with a human-written corpus. It uses "three key metrics inspired by the way experts evaluate security rules", and its case study is Sublime's Automated Detection Engineer (ADÉ). The abstract page does not name the metrics or give numbers. — [arXiv abstract](https://arxiv.org/abs/2509.16749)
- LLMCloudHunter (arXiv 2407.05194) generates Sigma rules from cloud threat-intel reports. On 12 CTI sources, 99.18% of generated Sigma candidates converted successfully into Splunk queries, and API-call extraction reached 92% precision. This shows that *syntactic validity checks* (does the rule compile/convert?) are an automatic first gate. — [LLMCloudHunter](https://arxiv.org/pdf/2407.05194)
- AutoSigma (arXiv 2608.19011, 2026) uses "an LLM-as-a-Judge mechanism in which two LLMs work in an adversarial collaboration to iteratively refine the Sigma rules", and template-based rule grounding. — [AutoSigma](https://arxiv.org/html/2608.19011v1)
- Sigma-Hunter (arXiv 2610.09007, Oct 2026) scores generated rules on "syntax validity, approximate field consistency, detection logic, completeness, rule selectivity, and log-source alignment". Selectivity is the false-positive dimension. — [Sigma-Hunter](https://arxiv.org/html/2610.09007)
- CTI-REALM (arXiv 2603.13517) is a benchmark of agents generating detection rules. Its related-work section cites SigmaGen (fine-tuned for Sigma) and RuleGenie (which removes redundancy across a rule set). — [CTI-REALM](https://arxiv.org/pdf/2603.13517)
- Weak evaluation warning: one YARA-generation task (arXiv 2509.23573) is scored with **BLEU**, which measures how closely the rule's text matches a reference, not whether it detects anything. — [arXiv 2509.23573](https://arxiv.org/html/2509.23573v5)
- I found no Sigma-vs-YARA side-by-side evaluation. — (search result summary; see Gaps)

**workerd specifics**
- workerd is "a JavaScript / Wasm server runtime based on the same code that powers Cloudflare Workers". It is Apache-2.0, and its uses include self-hosting Workers and local development/testing. — [workerd README](https://github.com/cloudflare/workerd)
- It "tries to isolate each Worker so that it can only access the resources it is configured to access". Configuration "uses capabilities instead of global namespaces", which the README says makes it "immune to SSRF attacks". With nanoservices, "the callee runs in the same thread and process", so calls between Workers are cheap. — [workerd README](https://github.com/cloudflare/workerd)
- **Security warning (load-bearing):** "workerd on its own does not contain suitable defense-in-depth against the possibility of implementation bugs". For untrusted code "you must run it inside an appropriate secure sandbox, such as a virtual machine". — [workerd README](https://github.com/cloudflare/workerd)
- Config is in **Cap'n Proto text format** (`using Workerd = import "/workerd/workerd.capnp";`). The full reference is in the comments of `src/workerd/server/workerd.capnp`. `workerd serve wrangler.jsonc` also works, but supports only a limited set of fields. — [workerd README](https://github.com/cloudflare/workerd); [workerd.capnp](https://github.com/cloudflare/workerd/blob/main/src/workerd/server/workerd.capnp)
- **Running from Node/npm:** "Prebuilt binaries are distributed via npm. Run `npx workerd ...`". Command: `workerd serve my-config.capnp`. Prebuilt requirements: macOS 13.5+ with the Xcode CLT; Linux glibc 2.35+; x86_64 with SSE4.2/CLMUL or arm64 with CRC. Version numbers are dates (the newest compatibility date supported). — [workerd README](https://github.com/cloudflare/workerd)
- **Network capability:** workerd creates a default `"internet"` service that backs global `fetch()` "unless you specify a different globalOutbound". The default blocks private addresses (SSRF). Network services accept `allow`/`deny` lists (CIDR, or the classes `"public"`, `"private"`, `"local"`, `"network"`), and `deny` takes precedence. Setting **`globalOutbound = null`** removes `fetch` access completely. — [workerd issue #93](https://github.com/cloudflare/workerd/issues/93); [workerd issue #8049](https://github.com/cloudflare/workerd/issues/8049); [Mintlify workerd services docs](https://www.mintlify.com/cloudflare/workerd/configuration/services). The `null` detail comes from a secondary write-up ([flaviocopes](https://flaviocopes.com/workerd/)). Confirm it in `workerd.capnp`.
- **Disk is also a capability:** a `disk` service exposes a directory over HTTP, read-only by default (`writable = true` to allow writes, `allowDotfiles` controls dotfiles). A Worker sees it only if it is given a binding. — [workerd issue #93](https://github.com/cloudflare/workerd/issues/93); [Mintlify services docs](https://www.mintlify.com/cloudflare/workerd/configuration/services)

**Alternatives for sandboxing untrusted JS in Node**
- **`node:vm`:** the official docs (v26.13.0) say "The node:vm module is not a security mechanism. Do not use it to run untrusted code." A known escape uses `this.constructor.constructor` to reach the host's `Function`. — [Node.js vm docs](https://nodejs.org/api/vm.html); [Advanced Web Machinery notes](https://advancedweb.hu/shorts/my-notes-on-the-security-concerns-of-a-javascript-sandbox-with-the-node-js-vm-module/)
- **vm2** runs on top of `node:vm` in the same process and has had critical escapes, including one rated CVSS 10. — [Snyk/Medium](https://medium.com/@snyksec/the-security-concerns-of-a-javascript-sandbox-with-the-node-js-vm-module-b1a63e128e04); [vm2 repo](https://github.com/patriksimek/vm2)
- **isolated-vm** (separate V8 isolates): "currently in *maintenance mode*". "Use of isolated-vm to run untrusted code does not automatically make your application safe". It advises keeping it "in a different nodejs process than other critical infrastructure" and never leaking `Reference`/`ExternalCopy` objects to guest code. `memoryLimit` is "more of a guideline", and "a determined attacker could use 2-3 times this limit" (default 128 MB, minimum 8 MB). `timeout` has no default. Node 20+ needs `--no-node-snapshot`. Compatibility: Node 22 → 5.x/4.x, Node 24 → 6.x/5.x, Node 26 → 7.x, and odd-numbered Node versions are unsupported. It needs a native build toolchain. Data crosses only as transferable/copied values. — [isolated-vm README](https://github.com/laverdet/isolated-vm)
- **quickjs-emscripten** (the QuickJS interpreter compiled to WASM) claims to "safely evaluate untrusted Javascript (supports most of ES2023)". Limits come from `setInterruptHandler` (deadline, e.g. `shouldInterruptAfterDeadline(Date.now()+1000)`), `setMemoryLimit` and `setMaxStackSize`. Handles must be `.dispose()`d manually. For stronger isolation it recommends separate runtimes per source, or separate WASM modules. — [quickjs-emscripten](https://github.com/justjake/quickjs-emscripten); [QuickJSRuntime docs](https://github.com/justjake/quickjs-emscripten/blob/main/doc/quickjs-emscripten/classes/QuickJSRuntime.md)
- A known gap in QuickJS-WASM: measured on quickjs-emscripten 0.32.0, `setMemoryLimit` "does not charge string payload bytes", so a guest appending 10 KiB strings grew past a 2 MiB limit. That project relies on a deadline interrupt plus a host watchdog (1.5× deadline) and throws away the runtime after any limit error. — [icecream-sandbox](https://github.com/is-cream/icecream-sandbox) (third-party measurement)

### Inferences
- **"Generate ahead of time, verify, then freeze" pipeline (my design from the sources above):**
  1. The policy author describes the category ("US SSN", "payment card number") and supplies *positive and negative* examples. The negatives include near-misses: phone numbers, student IDs, ISBNs, order numbers and dates.
  2. The LLM writes a **pure function** with a fixed signature: `detect(text) → [{type, start, end, confidence}]`. No imports, no I/O.
  3. Automatic gates, in the order the Sigma literature uses: (i) parses/compiles; (ii) passes every positive and rejects every negative on a held-out split it never saw (the Sublime holdout method); (iii) a static check for banned constructs (`fetch`, `import`, `eval`, `Function`, timers) and a regex-safety check against ReDoS; (iv) a per-call time/memory budget under fuzzed input; (v) a judge/repair loop limited to N rounds (AutoSigma-style). Only versions that pass are pinned by content hash and recorded with their test results.
  4. **Generation is offline and human-approved. Runtime is deterministic.** The model is never called on the hot path to write code, which also fits this project's "no model-generated code" scope rule unless the user lifts it explicitly.
- **Sandbox choice for this local Node demo:**
  - *workerd* fits best if the user wants to keep their previous approach. Run each validator as a Worker with no bindings and `globalOutbound = null`, and call it from the Hub over a localhost socket. The README's own warning means it should run in a VM/container if the code is truly untrusted. For code that is generated *and then reviewed and pinned*, the risk is lower, but it is still not zero.
  - *quickjs-emscripten* is the simplest in-process choice (pure WASM, no native build, no extra process). The cost is speed (it is an interpreter) and the string-memory gap, so always set a deadline.
  - *isolated-vm*: real V8 isolates and fast, but in maintenance mode, a native build, `--no-node-snapshot`, and a soft memory limit.
  - *node:vm / vm2*: do not use them for this.
- Regex-only validators (no general code) would cut the attack surface further. A generated *regex plus checksum spec* could run in a fixed, trusted engine instead of running arbitrary JS. That needs only ReDoS-safe patterns, and the project has already met this problem with the A2UI renderer's ReDoS detector (CLAUDE.md).

- I found no primary research specifically on LLM-generated **PII regex/validators** with false-positive measurements. The evidence is from security detection rules (Sigma, email).
- I could not get the Sublime paper's three metric names or numbers from the abstract page. Read the PDF.
- I did not verify the current workerd npm version or release date (the README's releases section came back empty).
- `globalOutbound = null` semantics are from a secondary source. Confirm them in `workerd.capnp`.
- I found no published benchmark of call latency for workerd vs. isolated-vm vs. QuickJS-WASM for small validator functions.

## (c) How to evaluate a guardrail's accuracy

### Takeaway
Measure each category and each direction separately: precision, recall and false-positive rate. Measure over-refusal on deliberately "scary but safe" prompts (XSTest-style). Keep a frozen golden set as a regression gate. Calibrate thresholds on held-out data, then roll out in detect/shadow mode, where the guardrail reports but does not block, before you enforce anything. Use red-team tools (garak, PyRIT, promptfoo) to find misses, and add every confirmed miss to the golden set.

### Cited Findings
**Datasets**
- **OpenAI moderation eval** (Markov et al., "A Holistic Approach to Undesired Content Detection in the Real World", AAAI 2023, 37(12):15009–15018; arXiv 2208.03274): a public test set of **1,680** samples (`samples-1680.jsonl.gz`, from `openai/moderation-api-release`). The labels are S, H, V, HR, SH, S3, H2, V2. A missing label means "we do not know the label", so you must choose how to treat missing labels. One ACM paper sets them to 0. The paper names the steps that matter: taxonomy, labelling instructions, data quality control, and active learning "to capture rare events". — [AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/26752); [HF dataset](https://huggingface.co/datasets/mmathys/openai-moderation-api-evaluation); [ACM 10.1145/3700789](https://dl.acm.org/doi/10.1145/3700789)
- **ToxicChat** (Lin et al., 2023): 10,166 real user prompts with toxicity annotations, split half for training and half for testing (the "ToxicChat-1123" test split is common). The count comes from a citing paper (GradSafe), not the original. — [GradSafe, arXiv 2402.13494](https://arxiv.org/pdf/2402.13494)
- **XSTest** (Röttger et al., NAACL 2024): **250 safe prompts** across 10 types (25 each) that well-calibrated models should *not* refuse, and **200 unsafe contrast prompts** (8 types × 25) made by minimal edits to the safe ones. The main failure it found was "lexical overfitting", where models react to safety keywords instead of meaning. This is the over-refusal/false-positive test. — [ACL Anthology](https://aclanthology.org/2024.naacl-long.301/); [HF walledai/XSTest](https://huggingface.co/datasets/walledai/XSTest)
- **BeaverTails** (Ji et al., NeurIPS 2023 D&B; arXiv 2307.04657): 333,963 QA pairs across **14 harm categories** (330k version, about 3.34 annotations per pair) and 30,207 pairs (30k version). Labels are multi-label, and "safe" means risk-neutral across all categories. About 55% are unsafe. The largest unsafe categories are "Non-Violent Unethical Behavior" (31.3%) and "Hate Speech, Offensive Language" (16.4%). Responses come from Alpaca-7B. — [BeaverTails](https://arxiv.org/html/2307.04657v3)
- **ai4privacy/pii-masking-400k:** synthetic, 4th iteration, 17 PII classes public (63 extended), languages en/fr/de/it/es/nl, JSONL train/validation, about 515 MB, licence "other". The newer flagship is `pii-masking-openpii-1.5m` (1.6M samples, 30 languages, 19 classes), plus domain splits (health, financial, location, work) of about 400k each. — [HF card](https://huggingface.co/datasets/ai4privacy/pii-masking-400k); [ai4privacy org](https://huggingface.co/ai4privacy)
- **Gretel synthetic PII:** `gretelai/synthetic_pii_finance_multilingual` ("Synthetic-PII-Financial-Documents-North-America"), cited in a 2026 paper that evaluates the OpenAI Privacy Filter across 32 PII benchmarks. That paper also cites NVIDIA Nemotron-PII and Dataiku Kiji PII. — [arXiv 2608.02616](https://arxiv.org/pdf/2608.02616). I did not fetch the Gretel card itself.
- RedactionBench (arXiv 2606.18782) is a newer PII redaction benchmark. It appeared in results, but I did not read it. — [RedactionBench](https://arxiv.org/pdf/2606.18782)

**Shadow/monitor-only rollout**
- Amazon Bedrock Guardrails "detect mode": set a policy's action to `NONE`, and "the guardrail takes no action but returns what it detects in the trace response". AWS lists three benefits: test policy combinations "without affecting customers", "analyze false positives or negatives and adjust", and enforce only after confirming. Example trace: `{"action":"NONE","confidence":"LOW","detected":true,"filterStrength":"HIGH","type":"VIOLENCE"}`. — [AWS docs](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-harmful-content-handling-options.html); [AWS ML blog](https://aws.amazon.com/blogs/machine-learning/build-safe-generative-ai-applications-like-a-pro-best-practices-with-amazon-bedrock-guardrails/)
- Detect mode differs from turning a policy off: it still evaluates and reports. It is a measurement tool and "protects nothing on its own". — [hidekazu-konishi deep dive](https://hidekazu-konishi.com/entry/amazon_bedrock_guardrails_implementation_deep_dive.html) (third-party)
- The Strands Agents SDK documents a shadow-mode hook pattern: log when the guardrail *would* have intervened (`GUARDRAIL_INTERVENED`) without blocking. — [Strands guardrails docs](http://strandsagents.com/docs/user-guide/safety-security/guardrails/)

**Threshold calibration**
- semantic-router v1's `fit()` turns raw similarity into calibrated probabilities from labelled examples, so a threshold can be set from a target such as "90% sure". — [Aurelio docs](https://docs.aurelio.ai/docs/semantic-router/v1/user-guide/guides/migration-to-v1)
- Llama Guard lets you read a continuous score from the first-token probability, so you can tune a threshold instead of taking the hard `safe`/`unsafe` text. — [Llama Guard paper](https://arxiv.org/html/2312.06674v1)
- Conformal prediction gives distribution-free guarantees for when to accept a cheap stage's answer. — [Conformal Cascade](https://arxiv.org/html/2607.25018v1)

**Red-teaming tools (late-2026 status)**
- **garak** (NVIDIA): a CLI scanner made of probes, generators and detectors. It has 33 probe categories with about 1–5 probes each, uses both keyword and learned detectors, and writes JSONL results. It is best for scanning the raw model and weaker at the application layer. — [aisecbench comparison](https://aisecbench.com/posts/best-llm-red-teaming-tools-2026/); [threatclaw](https://threatclaw.io/en/blog/llm-red-team-tools-garak-pyrit-promptfoo) (secondary)

### Inferences
- **Metrics to report, per category × per direction (student→agent, agent→student, professor→student):** precision, recall, false-positive rate, and **over-refusal rate** on a benign-but-scary set (XSTest-style, rewritten for a university: "how do I kill a Python process", "the history of the atomic bomb", "my student ID is 123-45-678"). For PII, also report **span-level** precision/recall (did it find the right characters?), not just "message flagged".
- **Datasets fit only parts of the problem.** The OpenAI eval, ToxicChat and BeaverTails cover offensive language and harmful intent. XSTest covers false positives. ai4privacy and Gretel cover PII spans, but they are synthetic and mostly non-US-specific, so add a hand-built US SSN/card set with near-misses: phone numbers, ISBNs, campus IDs, and Luhn-valid test card numbers in a "how do payments work" context. Use fictional data only, per project rules.
- **Golden-set regression:** a frozen, versioned file of labelled messages that runs in `npm test` against the deterministic stages (free and repeatable). It is the gate every regenerated validator must pass. The LLM stage is checked separately with a paid, budget-capped spot check, like the project's existing `eval:live` gate, because live judgments are probabilistic.
- **Rollout:** shadow mode first. The Hub records "would have blocked/redacted" telemetry without changing messages, people review the flagged items, and thresholds are set from that data. Then enforce category by category. This matches the Bedrock detect-mode pattern and fits the existing monitor channel, where telemetry only *reports* real events.
- **Human review:** sample both flagged items (to measure precision) and a random slice of passed items (to estimate misses, i.e. recall). If you review only flagged items, you can never measure recall.
