## Avoid these known problems

1. **The 3-second status poll must never trigger a CHRS lookup.** The Faculty view polls the Hub; `status()` once fetched the roster, so every poll was a paid call. Read the cache only; counts are null until a post or roster request fetched it.
2. **A cancellation offer must survive `roster_unavailable`.** The offer was cleared as soon as the answer was read, so after “Try again in a moment” a second “yes” had nothing to answer. Re-arm the offer, the post offer and a held “class” answer when the post fails for lack of a list, and test a second yes once CHRS is back.
3. **The quiz-publish text must still say “published”.** The generic “nothing was sent” made it sound as if Canvas did nothing, so he might publish twice. Use the quiz-specific sentence in section 4.
4. **Never post a fragment for “about X”.** “Inform the whole class about the midterm review” sent “The midterm review.” to 25 students. Ask “What should I tell your class about …?” and send his next reply.
5. **No stale “2 students”.** The publish prompt and the header used the two-person session list. Say “your students” and show no count until the roster count is known; keep the last known count after the 60 s cache expires.
6. **No header chips before the count.** Show only “Marketing 351” until the real count arrives.
7. **The Hub's roster request needs a `runId`.** Without it CHRS's own events (received, MCP call, reply) never reached the Topology.
8. **Identical event rows.** Two PeopleSoft tiles produced rows that both read “→ PeopleSoft”. The student records rows say “Student records”.
9. **No raw id in a route label.** Show the public name (“CHRS”), never the agent id.
10. **A node the page doesn't draw must not crash the stream.** An event for `chrs` before the node existed threw and put the live stream in a reconnect loop, which blocked the Faculty view. Ignore it and warn once per id.
11. **Roster IDs in the Hub are names and ids only.** Never emails or 888 IDs in the Hub, its telemetry or logs; the rows reach only the Faculty view, only while it is shown.
12. **A poll must not carry old rows.** Drop the roster rows from the page when another tab shows; a failed load retries on the next render.
13. **A reset in flight leaves no roster card.** Use a generation guard; the card says “Ask again to see your roster.”
14. **Keep the online count when the Hub's view is missing.** Don't overwrite a known online count with 0.
15. **The timeout budget must nest.** The spec's 15 s lookup could not sit inside CHRS's own 20 s; use 22 s for the lookup and 40 s for the Professor's publish, and test the order.
16. **A tagged single student also needs CHRS.** A tagged student must be on the roster; CHRS down refuses the post. Don't add a fallback list.
17. **Sign the `service` field only when present** so old three-field HR signatures stay valid, and include it in the dedupe hash.
18. **Don't let a staff answer start a new request.** “Tell the class” after the held-message question must not be read as a notify opening (`staffHolding()`).
19. **Full `npm test` under load can fail `hr-peoplesoft` “M3 session status” or “forged publishes”.** Re-run the file alone before blaming the change.
20. **Check by eye.** Open every screenshot against the mockup; a passing check is not a substitute.
21. **“Notify everyone” must not skip the privacy check.** “Notify everyone that Dr. Dabirian is sick today, no class” went to 25 students while the same words without the opening were asked about. Run the plain path's check (illness/leave/relative words, the open-card rule, the staff classifier) on the rest of the sentence and on the reply to “What should I tell your class about X?”.
22. **A waiting cancellation offer must not turn “notify everyone that …” into a raw post.** It sent “Notify everyone that the review session is in room 204” verbatim with no “Sent to all 25 …”. Handle notify with content under a cancellation offer and keep the offer open.
23. **Delivery names must never become raw ids.** After the Hub's 60 s cache expired rows read “student-mariana-aguilar isn't online”. Keep a memory-only id → name map in the Hub for students it delivered to; fall back to “A student” / “this student”, never the id.
24. **The timeout chain must include the Faculty model.** Model 45 s + publish 40 s exceeded the 80 s proxy. Add `professorModelMs`, test the sum, raise proxy/UI to 100/105 s.
25. **“Tell everyone to read chapter 5” sent “To read chapter 5 before Thursday.”** Turn `to <verb>` into “Please <verb> …”.
26. **Classmates' names must not ride the shared state.** Delivery names were in `/author/state`, which reaches the student's page too. Serve names only through the Faculty view's roster fetch and drop them when the tab hides. Fictional ids (`student-<first>-<last>`) do appear in `data/` files and recipients (owner ruling); names, emails and 888 IDs do not.
27. **Docs: `STUDENT_RECORDS_URL` defaults to 41249** in the CHRS process (only the harness uses port 9); a rebuild that followed “port 9” broke `npm run demo`. And the README's “not built” list must not claim whole-class notices are missing.
28. **An HR card edit during “what should I tell your class about …?”** (“make it Dec 7 instead”) was posted to 25 students. Check the open card first — but only for a clear card edit (`tellGoesToCard`, problem 32).
29. **The status poll must not wait on re-publishing.** It re-sent every uncertain post in sequence, each up to 40 s; polls every 3 s stacked. Re-publish in the background with an in-flight guard.
30. **Remove dead wiring.** The quiz desk's unused `roster` parameter (and the Faculty agent's `lastRoster`) were removed.
31. **A failed class notice after a Canvas publish must stay visible.** With the class list unavailable the published card showed “Sending…” forever and no button (the card drew the Publish button only before publishing). Carry `noticePending` + the sentence in the `quizCard` summary and draw the sentence and “Publish & notify students” on the published card.
32. **A day or time is not a card edit.** While “What should I tell your class about …?” waited with an HR card open, “We leave from the main entrance at 9 AM on Friday.” went to HR and changed the card. Only a clear edit cue, hours, an absence name or a leave / illness / relative word sends that reply to HR; and “we leave from …” is not leave.
33. **Roster questions must not hit the staff question.** “How many students are enrolled?”, “Is Sam Student in my class?” and “what's Mariana Aguilar's email?” got “Should I file this as time off with HR, tell the class, or both?”. Read them in code before the staff desk; never put an email, ID or major in the chat (highlight the row on the card instead).
34. **A roster question or “Thanks” is not an answer to the held question.** While the HR / class / both question waited they were read as unclear answers, counted toward the re-ask, and could drop the held message. Answer them and keep the question waiting unchanged.
35. **A bare “notify everyone” must arm the wait.** It asked “What should I tell your class?” but the next reply went to the staff desk. Arm the same 15-minute wait as “… about X”.
36. **Don't lose the subject.** The reply to “… about the guest speaker” reached students as “She is a brand manager …” with no subject. Send “About X: <reply>.” unless the reply already names X.
37. **Name parsing:** don't exclude month names by prefix — “Jane” matched `jan…` and “Is Jane Doe in my class?” fell through to the staff question. Use whole month words.
38. **A count asked of the assistant came from the wrong list.** “@assistant how many students are in my class?” → “There are 2 students in your class: Alex Student (@alex) and Sam Student (@sam).” Run the code roster readers on @assistant messages, give the model the class size, and never show it the session list as the class.
39. **@-tags must use the roster.** “@mariana please resubmit your assignment” → “There's no @mariana in Marketing 351”, though she is enrolled; the Faculty view also suggested only Alex and Sam. Resolve tags (@first, @last, @first-last) against CHRS names; suggest from a Faculty-only names fetch.
40. **A roster question was posted to the whole class.** “can you email me the roster?” reached all 25 students; “export my roster to excel” got the HR / class / both question. Show the card with “I can't email or export your roster from here, but here it is to look at.”, and never post a question about the roster or “my students”.
41. **Level and major questions fell through.** “who are my seniors?” got the HR question; “how many seniors are in my class?” (as a reply) got “Okay, nothing was filed or posted.” Read them in code (highlight or count) and keep which rows matched in memory only.
42. **A real class message was lost under the held question.** “tell my students the midterm is postponed” got “I'm still holding …”, then “Let everyone know that grades are posted” got “Okay, nothing was filed or posted.” and was never sent, with no notice. A notify with content is a new message; a dropped question always says when the last reply wasn't sent.
43. **The published quiz card lost its title and due date after a reload** (“The quiz is open in Canvas (quiz #4821).”). Carry `title` and `dueAt` in the `quizCard` summary once published, and after a reload ask for the draft only while the card is a draft (a published card's draft request answered 404 in the console).
44. **“make it 4 hours instead” didn't change an open time-off card** (it stayed 8 hours): the hours reader refuses any message with a correction word (“make it”, “instead”) so “4 or 5 hours” is never guessed. For a follow-up on an open card, strip the edit words around one hour value (`readEditHours` in `src/hr-intent.js`, a word loop on input capped at 200 characters — no backtracking regex) and read it; “make it 4 or 5 hours” still reads nothing.
45. **Praise was held back as a roster question.** “What a great class, my students rock!” got “That reads like a question about your roster …”. An exclamation, or “what a/an …”, is not a question: it posts to the class.
46. **“Thanks” with nothing waiting got “Should I file this as time off with HR, tell the class, or both?”** Answer “You're welcome.” whenever no cancellation offer is waiting (the held question, if any, keeps waiting).
47. **Model names and “AI” were on screens people read** (“Course assistant · claude-haiku-5-5”, “Drafted by claude-haiku-5-5”, “AI draft”, “Draft one more with AI”, “The AI drafted 3 of 5”, header “Router: live (claude-haiku-5-5)”). The owner: “there should not be any models exposed”. Keep model names in Topology and Agent activity only; guard the person-facing strings with a test.
48. **“@assistant what topics have we covered so far?” got “nothing has been sent to students yet, so no topics have been posted through this console.”** Topics taught come from the term schedule, not from what was sent: answer it in code from the schedule (taught topics as a numbered list, then the next one), give the assistant's model the same schedule, and keep words like “console” and “data” out of its answers.
49. **“anyone not a business major?” was POSTED to all 25 students** as a class message (“Asking whether non-business majors are enrolled”) and nothing answered him. The owner: “I asked the question and no response was given the faculty should be able to ask questions about the roster”. Only fixed phrasings were recognised. Recognise any question that names a roster attribute in code, let the model turn it into a query over the allowed values only (never an answer, never a row), check and run it in code, answer with counts and highlighted rows, and never post it.
