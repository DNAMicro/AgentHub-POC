PART 10: AG-UI FOR THE CONVERSATION, AGENT ACTIVITY AND PROFESSOR VIEW

Your words: “why not make AG-UI step 10 so we have the right infrastructre for filling forms from the UI” · “just the conversation, and the agent activity and the professor not the topology” · “make AG-UI the only item for Step 10 and then step 11 is to fill from the chat”.

Continue the existing application from Parts 1–9. Inspect the repository, running services and UI first. This is an **infrastructure step**: the Conversation tab, the Agent activity tab and the Professor view receive their updates as **AG-UI** (Agent–User Interaction protocol) events, and chat questions are sent as AG-UI run input — so Step 11 can carry the open form's values to the Student agent in AG-UI's run `state`. **Nothing the student or professor sees changes** (including after a reload and with several tabs open), and no new feature is added.

## 1. Where AG-UI sits

| Layer | Protocol | Carries |
| --- | --- | --- |
| Agent ↔ agent | A2A (unchanged) | Student ↔ Hub ↔ Tutor / Library / Professor |
| What UI to show | A2UI v0.9 (unchanged) | forms and generated loan surfaces — carried **inside** AG-UI events to the screen |
| Agent ↔ screen | **AG-UI 1.0** (new) | Conversation tab, Agent activity tab, Professor view |
| Monitoring | the existing stream `/api/events` (unchanged) | Topology tab, the hop-by-hop strip, tests |

**`/api/events` stays complete and unchanged.** Topology labels, the hop-by-hop strip (`flowStep`) and the test harness (`chatVia`, `formVia`, 12 test files) all read it; it keeps every event it carries today, including reply text and received A2UI payloads. **AG-UI is a second view built from the same real events** by a translator in the UI server (`src/ag-ui-bridge.js`): it never invents an event that didn't happen and never reorders a run. Update CLAUDE.md's “Three channels” rule to say exactly this.

## 2. Packages

Pin exactly: `@ag-ui/core@1.0.3`, `@ag-ui/client@1.0.3`, `@ag-ui/encoder@1.0.3`, and `zod` (the version `@ag-ui/core` resolves to, pinned as a direct dependency: schema validation needs it and it is only an optional peer of core). `@ag-ui/client` declares its own dependencies with `^` ranges (rxjs, fast-json-patch, …): commit `package-lock.json` so they resolve the same everywhere. Read the real types in `node_modules/@ag-ui/*/dist/*.d.ts`: event names are the `EventType` enum (`RUN_STARTED`, `RUN_FINISHED`, `RUN_ERROR`, `TEXT_MESSAGE_START/CONTENT/END`, `STATE_SNAPSHOT`, `STATE_DELTA`, `ACTIVITY_SNAPSHOT`, `CUSTOM`, …); run input is `RunAgentInput { threadId, runId, protocolVersion?, state?, messages, tools, context, forwardedProps?, resume? }`; `PROTOCOL_VERSION` is `"1.0"`. Server: `EventEncoder.encodeSSE`. Browser: `@ag-ui/client` bundled by a **second entry** in the existing esbuild step (`npm run build:ui` → `public/vendor/ag-ui.js`). No frontend framework, no CopilotKit.

## 3. Transport: one connection per page, AG-UI runs opened by POST

Verified in the installed client: `HttpAgent` does **not** implement `connect()` — the base `AbstractAgent.connect` throws `AGUIConnectNotImplementedError` and `connectAgent()` swallows it and returns, so idle events would silently never arrive. The client's verifier also requires every event sequence to start with `RUN_STARTED` and allows nothing but a new `RUN_STARTED` after `RUN_FINISHED`. So:

- **One connection per browser page** (`GET /api/ui/stream?monitor=<id>&student=<id>`). Browsers allow only **6 open connections per server**: a page holding the monitoring stream plus two AG-UI streams blocked every request as soon as two windows were open (found while rehearsing the live walkthrough, which opens a Topology popup). This one SSE stream carries three channels, each event named by its channel — `monitor` / `monitor:hello` / `monitor:truncated` / `monitor:replayed` (exactly the `/api/events` payload), `student` (the Student agent's AG-UI events) and `professor` (the Professor view's AG-UI events). It writes no shared `id:` line; each channel's cursor is inside its data. The server builds it by handing each channel writer (monitor, `agui.connect`, `professorAgUi.connect`) an adapter that renames its SSE events. `/api/ag-ui/stream` and `/api/ag-ui/professor/stream` stay for tests and other clients.
- **Each AG-UI channel goes to its own agent**: a small subclass of `HttpAgent` (`src/ag-ui-stream-agent.js`, `StreamAgent`) that **overrides `connect()`** to read either its own GET stream or one channel of the page's connection (`events`). The channel must be a **buffered channel** (`bufferedChannel()`): the client subscribes a moment after `connectAgent()` is called, so a plain rxjs `Subject` dropped the opening snapshot, `hello` and the whole history replay (seen as an empty chat after a reload). The page creates the agents right after `monitor:hello` (it always comes first), so a UI-server restart is known before any AG-UI event of the new process reaches a verifier. **Every connected tab receives every event** (dedupe by event ID), as before.
- **A chat question starts a run with a POST of AG-UI run input** (`POST /api/ag-ui/runs`, body = `RunAgentInput`). The server reads **only the last user message** (and, from Step 11, `state`), never trusts the `messages` history, and keeps the existing 64 KB body limit (the browser sends only the new message, not the whole conversation). The **server** still creates the run ID (it owns run state); the browser's `runId` is replaced by the server's, returned in the 202 answer as today. `POST /api/runs` stays for tests and old callers.
- **One strict run sequence per stream — no event is ever outside a run.** The installed client's verifier refuses `RUN_STARTED` while a run is open and refuses any event before the first run or after a finish; a verifier error ends the stream, and replaying the same order would fail again. So the bridge keeps one sequence (shared by every tab of that stream):
  - **While a run is open** (a student chat run can last up to the chat timeout), events that arrive meanwhile — a lesson, a receipt, console entries, a form's lifecycle change — go **inside that run** as `CUSTOM` events tagged with their own origin (`origin: 'inbox' | 'activity' | 'form' | …`) or as `ACTIVITY_SNAPSHOT` / `STATE_DELTA`.
  - **Between runs**, events are batched (≈150 ms) into one short **server-opened run** (`RUN_STARTED` → the events → `RUN_FINISHED`), named by a `CUSTOM` `server_run` marker with what caused it.
  - A **reconcile** of an uncertain send is a new run with `parentRunId` = the original run. A run that errored is never restarted with the same ID.
  - Test: a lesson and console entries arriving during a slow chat run (`TUTOR_MOCK_DELAY_MS`) land inside it, and the client's own verifier accepts the whole stream.
- **Event IDs, resume and reload only at run boundaries.** `EventEncoder.encodeSSE` writes only a `data:` line and AG-UI events have no ID field: write the SSE `id:` line yourself (`<bootId>:<seq>`) and carry the same ID in the event's `metadata`. A `Last-Event-ID` resume or a `UI_HISTORY_LIMIT` cut **re-sends the open run from its `RUN_STARTED`** (never starts mid-run); the browser's `connect()` drops events it already has (by ID) before the verifier sees them. On connect the server replays the history this way, then a `CUSTOM` `replayed` marker (and the `truncated` notice when history was cut), so the browser rebuilds exactly what it shows today through the same rendering code.
- **A UI-server restart is handled by the browser** (a new process can't close the old one's run): the page sees the new `bootId` in `monitor:hello`, resets both sides (`resetMonitor()`, `resetConversation()`) and starts fresh agents with an **empty dedupe list** and no cursor; a `StreamAgent` that still meets a new `bootId` prefix in an event ID ends its Observable (`bootChanged`). Dedupe state lives and dies with one subscription (the client's verifier is per `connectAgent` call: a fresh verifier with a stale dedupe list would drop the re-sent `RUN_STARTED` and fail). Test: restart the UI server during a slow chat run.
- **Snapshot before delta, always:** every connect — and every reconnect after a history cut — begins its first run with a fresh `STATE_SNAPSHOT` of the current form lifecycle state; never send a `STATE_DELTA` before a snapshot in the same subscription (a delta without its snapshot fails with only a console warning, and the form would show the wrong state). Test: a cut history, then a lifecycle change.
- **Write a whole reply as one block** (`TEXT_MESSAGE_START`, `CONTENT`, `END` together): the verifier refuses `RUN_FINISHED` while a text message is open. Give every `ACTIVITY_SNAPSHOT` its own `messageId` (`replace` defaults to true; a reused ID overwrites the earlier entry).

## 4. Conversation tab

- **Split the browser's event code in two.** `monitor(event)` (fed by the `monitor` channel) owns Topology, the hop-by-hop strip (`resetTimeline`, `flowStep`, the strip's error line), the Hub-telemetry badge and Topology's half of `applyTopology(snap, { topo, dom })`; `handle(event)` (fed by AG-UI, turned back into the app event it carries) owns the chat, the consoles, forms, the inbox and the screen half. **The strip is cleared only by the monitor side** (`clearStrip()` on `conversation_reset` and on restart): the two channels replay independently after a reload, and the AG-UI side's “New conversation” used to wipe a strip the monitor side had just rebuilt. Each side has its own dedupe set (`seen`, `seenMonitor`).
- Leaving the page ends the connection quietly (abort on `beforeunload` and `pagehide`; otherwise the client logs “Agent execution failed: network error”); a page restored from the back/forward cache reloads.

- A student chat run: `RUN_STARTED` → the student's own steps (`request_planned`, a clarifying question, a decline, `request_sent`, …) as `CUSTOM` events carrying the same data the screen uses today → the reply as `TEXT_MESSAGE_START / CONTENT / END` (the reply arrives whole from A2A: one content event, no fake streaming), with the reply's metadata (served by, colours, IDs) as a `CUSTOM` event → `RUN_FINISHED`, or `RUN_ERROR` with the existing sanitized codes. Delivery outcomes keep their meaning (`not_delivered`, `uncertain`).
- **Forms:** a form reply is a `CUSTOM` event carrying the received A2UI messages unchanged; the renderer still validates and renders them. A form's **first** state travels inside `form_received` (later changes are `form_lifecycle` events), so the bridge also writes `form_received` into the shared form state (a `STATE_DELTA` with no app event attached, so the form isn't drawn twice). The form **lifecycle** (`editing → submitting → accepted | rejected | confirmation_pending`, `cancelled`, `superseded`, review flags) is AG-UI shared state: `STATE_SNAPSHOT` / `STATE_DELTA` on `forms.<formId>.lifecycle`. **Form values are not in server state** — the browser owns them while the student types (Step 11 sends them in the next run's `state`). Form buttons still post A2UI actions to the existing endpoint; validation still runs in the three places.
- Every item the chat shows today keeps working: “You sent” summaries, receipts, ↩ Reply chips, meeting-time buttons, “check for answer” after an uncertain send, specialist colours, the waiting spinner. Keep every safety rule: `textContent` only, lesson text is content, logs scroll only through `followBottom`.

## 5. Agent activity tab

The Student, Hub, Tutor and Library consoles get their entries as `ACTIVITY_SNAPSHOT` events inside the current run or a batched server run (§3) (`activityType` = the console, `content` = the entry). Each one adds a message to the client agent's `messages`, so trim the agent's activity messages to the consoles' own limit (the same bound the consoles keep today) — the Hub's telemetry **after** its allowlist redaction (`redactTelemetry`; full content only with `HUB_TELEMETRY_SHOW_CONTENT=1`). Topology labels (`topo`) and heartbeats are not sent on AG-UI. Console history is replayed on reload like the chat.

## 6. Professor view

The Professor view uses **its own AG-UI agent instance and its own stream** (`GET /api/ag-ui/professor/stream`): a `STATE_SNAPSHOT` replaces an agent's whole state, so sharing the student's agent would wipe the student's form state, and its runs would collide with the student's. The professor's chat with the course assistant is an AG-UI run per message (`POST /api/ag-ui/professor/runs` → `RUN_STARTED` → the assistant's reply or the direct post's result → `RUN_FINISHED` / `RUN_ERROR`). The posts list and per-student delivery states are shared state: the **UI server** now fetches the Professor state through the Hub's developer proxy (as the browser's 3-second poll does today) while at least one Professor view is connected, and on the telemetry events that already trigger a refresh, and sends `STATE_SNAPSHOT` when it changed. (So the hidden Professor view is already filled in before it is opened — the only difference the before/after check found; once opened it is identical.) The route stays browser → UI server → Hub → Professor; every non-GET route keeps its origin guard; `@assistant`, `replyTo`, operation-ID dedupe and “one message at a time” behave as in Step 9.

## Avoid these known problems

- **Browsers allow 6 connections per server — keep one per page.** Three long-lived streams per page (monitoring, AG-UI, Professor) blocked every request once a second window was open; the walkthrough's question was never sent. Multiplex the channels on one connection (`/api/ui/stream`) and test with three windows open.
- **A plain `Subject` drops what arrives before the client subscribes.** Use `bufferedChannel()`; test that events emitted before `connectAgent()` subscribes are delivered.
- **Two streams replay independently after a reload**: anything that clears monitor-owned DOM (the strip) must be done by the monitor side only.
- **A form's first state is in `form_received`**, not in a `form_lifecycle` event — put it in the shared state too.
- **Close the stream on `beforeunload` as well as `pagehide`**: on a reload the browser cuts the connection before `pagehide`, and the client logs it as an error.
- **Checking the change itself:** record the before/after screens on a fresh mock stack each time (the Professor console isn't cleared by New conversation, so a reused stack shows earlier entries), make the script's two professor posts sequential (they raced), run two “before” recordings and require them to be identical before comparing, and never run two rehearsal stacks on the same ports.

- **`connectAgent()` looks supported but does nothing on `HttpAgent`** (found in the installed 1.0.3 code before building): override `connect()` yourself, or idle events silently never arrive.
- **Don't move events off `/api/events`**: Topology, the hop-by-hop strip and the test harness read the same events. Build AG-UI as a second view.
- **Don't send form values as server state**: the browser owns them while the student types; a server copy goes stale. Carry them in the next run's `state`.
- **Never send an AG-UI event outside a run, and never two runs at once on one stream** (found in the second review): the client's verifier refuses both and ends the stream. Put arriving events inside the open run, or batch them into one short server run.
- **Resume and cut history only at run boundaries; write the SSE `id:` yourself** (the encoder writes only `data:`).
- **A restarted UI server can't close the old run; the browser must** (third review): on a new `bootId`, end the subscription and start fresh with an empty dedupe list. **Snapshot before delta** after every connect or history cut.
- **Give the Professor view its own agent and stream**: one `STATE_SNAPSHOT` replaces an agent's whole state.
- **Don't let the browser create run IDs or send the whole history**: the server owns run state, and the 64 KB body limit would refuse long conversations.
- (Carried) Don't run reset or destructive checks on the user's running demo — use a separate stack (`scripts/demo/rehearsal-stack.js`, `startStack`). Start live servers with `env -u ANTHROPIC_BASE_URL`, and the handed-over demo detached (`nohup … & disown`).
