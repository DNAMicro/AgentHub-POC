## 3. The quiz AI (`src/quiz-model.js`)

**Concrete specification** (Faculty's model; mode follows `PROFESSOR_MODE`, read at import)
- `draftQuiz` = one structured call (the schema is an object `{ "questions": [...] }`, because structured output must be an object) that writes `count` questions from the chosen topic's notes only; the prompt holds no other topic's text. Each question is vetted with `checkQuestion` and with a rule that no date appears that the notes lack; failures are dropped; if fewer than `count` survive, **one** repair call names the failures; still short -> the card says “The AI drafted N of M — add or draft the rest.” The token cap grows with the count. `draftOne` (“Draft one more”) is told the existing questions so it does not repeat them. Both clamp the count to 1–20.
- Haiku 5.5 rules as everywhere: no sampling parameters, `effort: "low"`, always check `stop_reason` (`refusal`, `max_tokens` -> model failed), `maxRetries: 0`.
- Mock mode builds labelled questions from the notes' key terms (“Which term matches: <definition>?” then “Which definition fits the term …?”). It strips the definition's trailing punctuation so a question never ends `.?`.

- **Failure table** (honest, never retried by itself; the same `operationId` on every retry):

  | What happened | Approve shows | Publish shows |
  | --- | --- | --- |
  | Canvas down, no session, or timed out mid-call | “Canvas didn't answer. Nothing is posted until it confirms — press Approve again; it won't post twice.” | “Canvas didn't answer, so the quiz may still be unpublished and nobody was notified. Press Publish again; it won't publish twice.” |

- Routes (all non-GET origin-guarded, strict keys, id formats checked): Faculty `POST /author/quiz-action` and `GET /author/quiz/:draftId`; Hub proxy `POST /dev/agents/:agentId/author/quiz-action` and `GET .../author/quiz/:draftId`; UI server `POST /api/professor/quiz/actions` (runs `checkQuiz` on approve, and `validateFinal`-style strict keys) and `GET /api/professor/quiz/:draftId`. ## Avoid these known problems

1. **Do not put the quiz notice's operationId in a form that breaks the id rule.** Use `quiz-notice-<draftId>` with a random draft id so it matches `/^[\w-]{6,80}$/` and never collides with a saved operation after Canvas restarts its numbering at 4821.
2. **Do not save the draft or the Canvas card to `data/`.** Canvas forgets quizzes on every start, so a saved Publish card could publish a different quiz with the same number. Keep them in memory; the outbox keeps outcome text only.
3. **Do not let a redraw wipe the card.** `renderProfessor` rebuilds the chat when its signature changes (every delivery poll). Keep the quiz card's element in place and put the quiz card and the hidden flag in the signature.
4. **Check for a quiz request before the staff desk.** `staffTurn` runs first today; without this a quiz request while an HR card is open goes to HR, the cancellation offer, the 10 s classifier, or out as a direct post. A `replyTo` message is the exception.
5. **Budget the whole quiz turn.** A draft call plus its repair plus an interpret call must fit inside the Hub's 80 s proxy; a recognised request therefore makes no interpret call.
6. **Per-source Topology labels.** `src/topology.js` hard-coded the three `mcp_*` labels to HR -> PeopleSoft; branch on the event's `source`, add `canvas` to the node names and the edge to `hop()`.
7. **The content hash must cover the quiz.** Add `quiz` to `contentHash` (long form when present) and to every place that carries `meeting`: Hub validation, stored lesson, delivery, Student inbox check, `lesson_received`. Assert old hashes did not change.
8. **Add the routes everywhere.** Faculty routes, the Hub's explicit proxy list, the UI server routes, the `prof-<operationId>` run id (or the UI drops the events), `canvas_session` in `CONFIG_EVENTS`, and `quizId` / `questionCount` in `SAFE_FIELDS`.
9. **The answer key never travels in the shared stream.** `/author/state` reaches the student's page; it carries a summary without questions or answers. Check the state, the Faculty AG-UI stream, the monitor and the student page for a `correct` key or `[data-correct]`.
10. **Start without Canvas.** With no `CANVAS_TOKEN` the Faculty agent still starts, shows “not configured” and answers “Canvas isn't connected, so nothing was sent.”; without `CANVAS_URL` it uses the closed port 9, never a real :41247.
11. **An empty topic from the model must not win.** In `pickQuizTopic`, `??` keeps an empty string; use `||`, and trim the live topic.
12. **Decide uncertain vs refused by structure, never by error wording.** An error with structured content is refused; everything else mid-call is uncertain; a schema failure means the call never ran, so it is uncertain and safe to retry with the same operationId; 5xx is uncertain.
13. **The tests need an injectable clock.** A Canvas server that uses the real clock makes tests depend on today's date. `CANVAS_NOW` is read only with `CANVAS_TEST_HOOKS=1`; invalid values stop startup; production ignores it. Pin the main test `before`, the log check and the live-planner race.
14. **Never pass an internal message to the caller.** A store throw is logged (operation id only) and rethrown as the generic “Canvas could not complete the call”; only the fixed refusal codes are emitted.
