# Gate checks by trigger, judge by context

*Research synthesis, Friday, Oct 30, 2026. Built from the four note files in `research_notes/AI gateway guardrail mechanisms/`. Each section separates **proven facts** (cited) from **interpretations** (my reasoning, labelled). Items the researchers could not confirm are collected in the "Unverified items" table near the end.*

The better mechanism is not "smarter scheduling of every check." It is a **trigger-gated detector table plus one context-aware model verdict, configured per hop**. Production DLP and secret scanners never run every validator on every input. A cheap trigger (a keyword, a digit run, an `@`) decides which detectors are even considered. A checksum or structural rule confirms the candidate. Nearby context words then set a confidence level, and only findings above a per-type minimum act. Guardrail platforms pick their checks **statically by configuration**, per direction and per intervention point, and no major vendor runs a learned router that chooses checks message by message. For the context-dependent categories (offensive language, harmful intent), the evidence favours a single structured call to a general model with a written policy over a small open guard model. Independent studies found Llama Guard missing most harmful prompts, and Granite Guardian over-blocking a quarter of benign ones. The Hub already calls Claude Haiku with structured output, so that call is the natural judge. The most surprising finding is about speed. A local micro-benchmark run by the researchers (not a primary source) put a dozen regexes on a 4 KB message at about 15–80 µs. Running every check is therefore not a speed problem at this scale. It is an **accuracy** problem, because every loose pattern adds false positives, which is exactly what went wrong with Presidio. The workerd approach still fits, with one caveat: workerd's own README says it is not a hardened sandbox for untrusted code. The safer path is to have the model generate validator *data* (pattern, checksum name, keywords, window), run it in a fixed, trusted engine, and gate every version on a held-out golden set.

## Production systems choose checks by configuration, not by message

**Proven facts.** AWS Bedrock Guardrails evaluates "the input… in parallel for each configured policy." If the input is blocked, the model is never called. Otherwise the response is checked against the same guardrail ([AWS: How Guardrails works](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-how.html)). Each content, word and PII filter can be switched on per direction, with its own action (`BLOCK`, `ANONYMIZE`, or `NONE`, which detects without acting). A disabled direction is not charged ([AWS: sensitive information filters](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-sensitive-filters.html)). Bedrock prices **regex and word filters as free** and model-based filters at $0.10–$0.15 per 1,000 text units ([AWS Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)). Cloudflare's Firewall for AI uses a Worker that "makes parallel, non-blocking requests to our different detection modules," so latency "will only be bounded by the slowest model used." It enforces a **hard 2-second cap**, then falls back "to any detections already completed" ([Cloudflare blog](https://blog.cloudflare.com/block-unsafe-llm-prompts-with-firewall-for-ai/)). Microsoft Foundry defines each control as a risk plus **intervention points** (user input, tool call, tool response, output) plus an action (annotate, or annotate and block) ([Microsoft Learn: Guardrails overview](https://learn.microsoft.com/en-us/azure/foundry/guardrails/guardrails-overview)). Google Model Armor has separate `sanitizeUserPrompt` and `sanitizeModelResponse` endpoints, each bound to a template, with org-level floor settings as a minimum ([Model Armor REST](https://docs.cloud.google.com/model-armor/reference/rest)).

The ordered, fail-fast alternative is also documented. LLM Guard's `scan_prompt` loops through scanners in list order, passes each scanner's sanitized text to the next, and stops at the first failure when `fail_fast=True` ([LLM Guard evaluate.py](https://raw.githubusercontent.com/protectai/llm-guard/main/llm_guard/evaluate.py)). NeMo Guardrails runs rails in a stage **sequentially by default**. Its docs warn that masking must not run in parallel with rails that "must evaluate its transformed output" ([NeMo configuration reference](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/configuration-reference)). agentgateway runs "regex check first, then model-based checks, then a custom webhook" ([agentgateway guardrails](https://agentgateway.dev/docs/standalone/latest/documentation/llm/prompt-guards/overview/)). LiteLLM adds a `during_call` mode that "runs in parallel with the LLM call to save latency" and can only block. It also notes that `post_call` on a stream is audit-only ([LiteLLM guardrails](https://docs.litellm.ai/docs/proxy/guardrails/quick_start)).

The cascade idea has published support outside the gateway products. Anthropic's Constitutional Classifiers++ uses a cheap first stage that **escalates rather than refuses**, so that stage can tolerate more false positives. A second stage judges each output together with its input. The design reached **0.05% refusals on harmless production traffic** with about 1% compute overhead ([Anthropic](https://www.anthropic.com/research/next-generation-constitutional-classifiers)). COEF-VQ escalates to a larger model only when the base model's entropy passes a threshold, and uses that stage mainly to **cut false positives** ([COEF-VQ](https://arxiv.org/pdf/2412.10435)). Llama Guard 3 returns every category verdict in **one call** (`unsafe\nS1,S2`), and the same template covers user turns and agent turns ([Meta Llama Guard 3 docs](https://www.llama.com/docs/model-cards-and-prompt-formats/llama-guard-3/)).

**Interpretation.** For the Hub, the lesson is to treat each A2A hop like a Foundry intervention point with its own declared check list, rather than inventing a per-message router. Inside a hop, the deterministic stage runs first and synchronously, because it is close to free. Only then does the one model check run, unless a definite deterministic block already decided the outcome. Masking, if you ever use it, must finish before the model sees the text. The Hub is better placed than agentgateway for this. agentgateway has an open issue saying there is "no first-class hook to inspect or mutate A2A message payloads" ([agentgateway #3610](https://github.com/agentgateway/agentgateway/issues/3610)). The Hub already terminates every A2A leg and parses the parts itself.

## Checksums and proximity keywords are what cut false positives

**Proven facts.** Microsoft Purview's credit card type requires 14–19 digits that "must pass the Luhn test," must match issuer formats, and excludes "reserved credit card numbers, such as the ones financial institutions use for testing." It reports **confidence 85** when a card keyword or an expiry date is within 300 characters, and **65** with the checksum alone ([Purview credit card](https://learn.microsoft.com/en-us/purview/sit-defn-credit-card-number)). Purview's US SSN type has "Checksum: No." **Every one of its four patterns requires an SSN keyword** ("SSN", "social security number", "Soc Sec", "SS#"…) within 300 characters. Confidence runs from 85 for the pre-2011 format down to 55 for unformatted randomized numbers ([Purview SSN](https://learn.microsoft.com/en-us/purview/sit-defn-us-social-security-number)). So in Purview, a bare 9-digit number with no keyword nearby is not an SSN. The SSA's structural rules can reject some invalid strings: no area 000, 666 or 900–999, no group 00, no serial 0000 ([SSA randomization FAQ](https://www.ssa.gov/employer/randomizationfaqs.html)). AWS Macie requires a keyword "within 30 characters" for certain types in unstructured text ([Macie keyword requirements](https://docs.aws.amazon.com/macie/latest/user/managed-data-identifiers-keywords.html)). Google Sensitive Data Protection uses hotword rules with character windows before and after a finding, which raise or lower the likelihood. Its example shows two same-shaped numbers where only the one next to "MRN" becomes `VERY_LIKELY`. A negative hotword ("Fake Social Security Number") drops `111-11-1111` from the results ([Google SDP hotwords](https://docs.cloud.google.com/sensitive-data-protection/docs/creating-custom-infotypes-likelihood)).

The trigger idea comes from network intrusion detection. Snort and Suricata attach a literal string to each regex and "launch the corresponding regex matching only if the string is found," because multi-string matching beats multi-regex matching "by two orders of magnitude" ([Hyperscan, NSDI '19](https://www.usenix.org/system/files/nsdi19-wang-xiang.pdf)). Secret scanners do the same. TruffleHog put all detector keywords into one Aho-Corasick pass and skips any detector whose keywords did not appear ([Truffle Security](https://trufflesecurity.com/blog/making-trufflehog-faster-with-aho-corasick)). Gitleaks runs a keyword check before each rule's regex and supports allowlists and stopwords ([Gitleaks README](https://raw.githubusercontent.com/gitleaks/gitleaks/master/README.md)). GitHub's token redesign shows how far format plus checksum can go. A prefix alone was expected to bring false positives "down to 0.5%," and a CRC32 checksum "virtually eliminates" them ([GitHub blog](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)).

The Presidio record matches the user's experience. Its FAQ says "a driver's license number… could be any 9-digit number," and its documented fixes are higher thresholds and removing recognizers you do not need ([Presidio FAQ](https://presidio.dataprivacystack.org/faq/)). In issue #2415, "Call me on 9848012345" scored DATE_TIME 0.85 against PHONE_NUMBER 0.4. Because the anonymizer keeps the highest score, the phone number became `<DATE_TIME>`. In a 240-message test, about a fifth of the phone numbers were labelled something else ([presidio#2415](https://github.com/data-privacy-stack/presidio/issues/2415)). Presidio's context enhancer lifts a weak regex from 0.01 to 0.4 when a context word appears ([Presidio context tutorial](https://github.com/microsoft/presidio/blob/main/docs/tutorial/06_context.md)). LiteLLM's guide warns that short strings get flagged as US_DRIVER_LICENSE ([LiteLLM Presidio](https://docs.litellm.ai/docs/tutorials/presidio_pii_masking)).

**Interpretation.** The table below is the researchers' reasoning from these sources. No vendor publishes measured precision or recall per technique, apart from GitHub's 0.5% estimate.

| Technique | Effect on false positives | Cost to recall | Fits |
|---|---|---|---|
| Checksum (Luhn; random digit runs pass only 1 in 10, a property of mod-10) | Large cut | Almost none | Cards, IBAN |
| Structural rules (SSN area/group/serial, card issuer prefix and length) | Moderate cut | Almost none | SSN, cards |
| Required keyword within N characters | Large cut | Real: an unlabelled SSN is missed | SSN (Purview, Macie) |
| Keyword as a confidence booster | Cut at the high tier only | Low tier kept | Block when high, warn when low |
| Known test and dummy values (4111 1111 1111 1111, 123-45-6789) | Cut | Tiny | Cards, SSN |
| Exact-value allowlist (course codes, the university phone) | Cut | None for real PII | Hub-specific values |
| Never use NER for blocking; fixed precedence (checksum types beat context-free types) | Removes the Presidio failure modes | Loses names and places (not required here) | All |

Two points matter most for the Hub. First, **SSN is the hard case**. Without a checksum, you must choose between requiring a keyword (Purview's choice: high precision, misses "my number is 123-45-6789") and accepting any well-formed 9-digit run at low confidence. Short chat messages make a 300-character window behave like "keyword anywhere in the message." A 30–50 character window is more precise. Second, the researchers' benchmark found that a trivial gate (does the text contain a digit or an `@` at all?) skips digit and email detectors on clean text in about 0.1–0.3 µs. A pure-JS Aho-Corasick pass was *slower* than plain V8 regexes at this size. A small keyword alternation regex is enough, and `re2` matters mainly for ReDoS safety, not for speed.

## A Haiku judge beats small guard models for context

**Proven facts.** Vendor model cards look strong, but independent results are mixed. A 2025 robustness study of 10 guard models found **Llama Guard "too permissive"**: 97–99% accuracy on benign prompts but only **4.5–21.8% detection** of harmful ones. Granite-Guardian-3.2-5B **over-refused 25.7%** of benign prompts. ShieldGemma-2B's accuracy swung 20.7 points depending on prompt wording. Qwen3Guard-8B (85.3%) and WildGuard-7B (82.8%) were the best balanced ([arXiv 2511.22047](https://www.arxiv.org/pdf/2511.22047)). An ICLR 2026 workshop benchmark found Llama Guard 12B and GPT-OSS Safeguard 20B "missing up to 75% of unsafe content" ([arXiv 2605.28830](https://arxiv.org/html/2605.28830v1)). Guard models are also **badly calibrated** under jailbreak attacks ([arXiv 2410.10414](https://arxiv.org/html/2410.10414v1)). On SORRY-Bench's 7,000+ human labels, GPT-4o agreed with humans 78.9% of the time, against 60.6% for WildGuard and 40.8% for Llama-Guard-2-8B ([SORRY-Bench, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/9622163c87b67fd5a4a0ec3247cf356e-Paper-Conference.pdf)). But LLM judges are not perfectly steady either: their inconsistency "can vary significantly by the chosen safety criteria" and by language ([arXiv 2605.31381](https://arxiv.org/html/2605.31381v2)). OpenAI says its policy-following gpt-oss-safeguard is "time and compute-intensive." It puts small high-recall classifiers in front of it ([OpenAI](https://openai.com/index/introducing-gpt-oss-safeguard/)).

On the narrow-classifier side, Llama Prompt Guard 2 (22M/86M) flags any text that "explicitly attempts to override prior instructions," even harmless text. Meta warns that application-specific traffic lowers accuracy ([Prompt Guard 2 card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M)). Small classifiers can run in Node through transformers.js. `Xenova/toxic-bert` ships a 111 MB quantized ONNX file ([HF](https://huggingface.co/Xenova/toxic-bert/tree/main/onnx)). But quantization hurt one Prompt Guard 2 86M export, which fell from 0.980 to 0.899 accuracy ([gravitee](https://huggingface.co/gravitee-io/Llama-Prompt-Guard-2-86M-onnx)). Among hosted options, Perspective API **shuts down on December 31, 2026** ([perspectiveapi.com](https://www.perspectiveapi.com/)). OpenAI's free omni-moderation covers 13 harm categories but no PII and no prompt injection ([OpenAI community](https://community.openai.com/t/upgrading-the-moderation-api-with-a-new-multimodal-moderation-model/958187)). Anthropic's constitutional classifiers protect Anthropic's own models and are not sold as a moderation API.

**Interpretation.** A university chat has many "scary but safe" messages: "how do I kill a Python process," the history of the atomic bomb, a mental-health question. These need context, which is the XSTest problem of "lexical overfitting" ([XSTest, NAACL 2024](https://aclanthology.org/2024.naacl-long.301/)). A Haiku call can take the conversation's recent turns, the hop (student input, agent reply, professor post) and a university-specific policy. It needs no GPU, and it reuses the Hub's existing `callModel` path, with no hidden retries and sanitized errors. One call should return every category at once (Llama Guard-style multi-label output) as a structured verdict, for example `{category, action: allow|flag|block, reason}`. Do not make one call per category. Treat its confidence as a hint, not a probability. Prompt Guard would misfire on students who write "ignore my last message," so it suits third-party content better than direct student turns. A local toxicity model is a reasonable *optional* first stage later, but it adds a large pinned dependency and a model download. **There is no published head-to-head of Claude Haiku as a moderation judge.** Its accuracy, latency and run-to-run consistency in this role must be measured on the Hub's own test set.

## workerd fits only behind an outer boundary or with data-only validators

**Proven facts.** workerd isolates each Worker so it "can only access the resources it is configured to access." It uses capabilities instead of global namespaces, and it ships prebuilt via `npx workerd` ([workerd README](https://github.com/cloudflare/workerd)). The same README states the key caveat: "workerd on its own does not contain suitable defense-in-depth against the possibility of implementation bugs." For untrusted code, "you must run it inside an appropriate secure sandbox, such as a virtual machine" ([workerd README](https://github.com/cloudflare/workerd)). Network access goes through a default `"internet"` service with allow and deny lists, and disk access is a capability too ([workerd issue #93](https://github.com/cloudflare/workerd/issues/93)). The alternatives are weaker or rougher. Node's docs say "The node:vm module is not a security mechanism" ([Node.js vm](https://nodejs.org/api/vm.html)). vm2 has had a CVSS 10 escape ([Snyk](https://medium.com/@snyksec/the-security-concerns-of-a-javascript-sandbox-with-the-node-js-vm-module-b1a63e128e04)). isolated-vm is "in *maintenance mode*," its `memoryLimit` is "more of a guideline," and it needs a native build and `--no-node-snapshot` ([isolated-vm README](https://github.com/laverdet/isolated-vm)). quickjs-emscripten runs QuickJS in WASM with deadline, memory and stack limits ([quickjs-emscripten](https://github.com/justjake/quickjs-emscripten)). One third-party measurement found its memory limit "does not charge string payload bytes" ([icecream-sandbox](https://github.com/is-cream/icecream-sandbox)).

Research on LLM-generated detection rules, mostly Sigma rules, converges on verification against examples. Sublime Security's framework uses "a holdout set-based methodology" against human-written rules ([arXiv 2509.16749](https://arxiv.org/abs/2509.16749)). Sigma-Hunter scores "rule selectivity," which is the false-positive dimension ([arXiv 2610.09007](https://arxiv.org/html/2610.09007)). AutoSigma refines rules with two LLMs acting as adversarial judges ([arXiv 2608.19011](https://arxiv.org/html/2608.19011v1)). Scoring rules by text similarity (BLEU) says nothing about whether they detect anything ([arXiv 2509.23573](https://arxiv.org/html/2509.23573v5)).

**Interpretation.** The user's earlier design was generated validators, written ahead of time, tested, approved, and run in workerd. Its core is sound, because generation stays off the hot path and runtime stays deterministic. But the sandbox question changes once validators are reviewed and pinned. The real risk is no longer hostile code. It is subtle wrong code: a bad regex, a ReDoS pattern, an over-broad match. A cleaner fit for this project is to make the model produce **validator specs as data** instead of JavaScript. A spec holds the trigger, the pattern (checked as ReDoS-safe), a checksum chosen from a fixed list (`luhn`, `ssnStructure`, `iban97`), keywords, window size, confidence tiers and actions. A small trusted engine in the Hub runs those specs, so there is nothing to sandbox. This also respects the project's scope rule against "model-generated code," and it matches the project's existing ReDoS concern with the A2UI renderer. If the owner wants general generated functions (for example using Zod or validator.js), run them in workerd as a separate process, with no bindings and outbound network removed, called over localhost. Treat that as reasonable for reviewed code on a local demo, but not as a security boundary for truly untrusted code. quickjs-emscripten is the in-process alternative, always with a deadline. Whichever path is chosen, each version should pass these gates before it is pinned by content hash: it compiles; it passes held-out positives and near-miss negatives it never saw; a static check finds no `fetch`, `import`, `eval` or timers; and it stays within a time budget on fuzzed input.

## Evaluate per hop and per category, in shadow mode first

**Proven facts.** Bedrock's detect mode (`NONE`) "takes no action but returns what it detects." AWS recommends it for testing policies "without affecting customers" and for analysing false positives before enforcing ([AWS docs](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-harmful-content-handling-options.html)). XSTest provides **250 safe prompts and 200 minimally edited unsafe contrasts** for measuring over-refusal ([XSTest](https://aclanthology.org/2024.naacl-long.301/)). The OpenAI moderation eval has **1,680 labelled samples**, and a missing label means "we do not know" ([HF dataset](https://huggingface.co/datasets/mmathys/openai-moderation-api-evaluation)). BeaverTails covers 14 harm categories ([arXiv 2307.04657](https://arxiv.org/html/2307.04657v3)). ai4privacy's pii-masking-400k is synthetic, with 17 public PII classes across six European languages ([HF card](https://huggingface.co/datasets/ai4privacy/pii-masking-400k)). Cloudflare logs only analysis results: "The request body itself (the prompt text) is not stored" ([Cloudflare blog](https://blog.cloudflare.com/block-unsafe-llm-prompts-with-firewall-for-ai/)).

**Interpretation.** Report precision, recall and false-positive rate **for each category on each hop**: student→agent, agent reply→student, professor post→student. Add an over-refusal rate on a university-flavoured XSTest-style set. For PII, measure span-level accuracy (were the right characters found?), not just "message flagged." Public datasets cover only parts of the problem. Add a hand-built, fictional US set of SSNs and cards with near-misses: phone numbers, ISBNs, campus IDs, dates, and a Luhn-valid test card in a "how do payments work" question. Keep a frozen, versioned golden file that runs in `npm test` against the deterministic stage, free and repeatable. Every regenerated validator spec must pass it. Check the Haiku judge's plumbing with the existing fake Messages API. Check its *judgment* with a paid, budget-capped spot check modelled on `eval:live`, because live verdicts are probabilistic. Then roll out in shadow mode: the Hub emits "would have blocked" telemetry (check names, verdicts, timings, never the text). People review the flagged items **and** a random sample of passed items, since reviewing only flagged items can never measure recall. Enforce category by category after that. garak and promptfoo can find misses, and each confirmed miss joins the golden set.

## Recommended architecture for the University Hub

**Interpretation (this whole section is my design, built from the sources above).** Put one module in the Hub, for example `src/guardrail.js`, and call it at three points the Hub already controls. **Inbound**: in the Hub executor, after signature checks and before the router. **Outbound reply**: when a specialist's answer returns, before it is relayed to the Student. **Professor post**: before a post becomes deliveries. Each point has a declared policy, so nothing runs "everywhere."

| Hop | Stage 0: deterministic (always, sync) | Stage 1: Haiku judge (one structured call) | On block |
|---|---|---|---|
| Student → Hub (chat text) | SSN, card, plus exact allowlist and test-value lists | Offensive language, harmful intent, self-harm (route to support wording) | Student told the category in fixed code-owned words; nothing forwarded |
| Specialist reply → Student | Card, SSN (a leak check on agent output) | Offensive language, harmful content | Reply withheld; student told a reply was held back and why |
| Professor post → Student | Card, SSN | Offensive language | Post refused to the professor with the reason; no delivery |
| Form submissions | Skip PII checks on fields that are *meant* to hold a name or email | None (form data never goes to a model, per project rules) | n/a |

Stage 0 is a data table, one row per detector. Each row holds a trigger (for example `/\d/`, plus a keyword alternation), a ReDoS-safe pattern, a validator from a fixed list, keywords with a 30–50 character window, confidence tiers, and a per-hop action. Precedence is fixed, so a checksum-validated type beats a context-free one. Cards: Luhn plus issuer rules means **high** confidence, so block. Test numbers are dropped. SSN: valid structure plus a nearby keyword means **high**, so block. Valid structure with no keyword means **low**, so it is passed to the judge as a hint rather than blocked. A definite Stage 0 block skips Stage 1. Otherwise, Stage 1 runs on every chat message on hops where it is enabled. It is one call that returns all categories, with the deterministic findings passed in as hints, so the judge can clear a low-confidence SSN that is really an order number. That follows the COEF-VQ split: the cheap stage aims for high recall, and the model stage clears false positives. To hide latency, the inbound judge can run in parallel with the Hub's router call, in the style of LiteLLM's `during_call`, and discard the routing result if the judge blocks. Every guardrail decision produces a Hub telemetry event with check names, tiers, verdicts and timings, never text. It passes the existing `redactTelemetry` allowlist and shows on the topology as a real hop. Message wording shown to the student comes from code, not from the model, so the reason is always accurate and safe to display. Validator specs are generated offline by a model, reviewed, gated on the golden set and pinned by hash. They are never generated at runtime.

## Open decisions for the owner

| Decision | Options | Why it matters |
|---|---|---|
| SSN without a keyword nearby | Block / send to judge as a hint (recommended) / ignore | Precision versus recall; Purview ignores it |
| Validators as data specs or as generated JS | Specs in a trusted engine (recommended) / JS in workerd or QuickJS | The project's scope rule forbids model-generated code unless lifted |
| Judge on every chat message, or only when Stage 0 or a cheap signal fires | Every message (simpler, paid) / gated (cheaper, may miss intent) | Cost and latency versus recall on harmful intent |
| Behaviour when the judge call fails or times out | Fail closed on outbound, open with a visible notice on inbound / closed everywhere | The project bans hidden fallbacks; a choice must be explicit |
| What a blocked outbound reply shows the student | "A reply was held back because…" / silent retry (not allowed by project rules) | The student must be told |
| Block versus flag for self-harm or distress | Block / answer with support wording and let the message through / hand to the professor | A university duty-of-care question, not a technical one |
| Mask PII and forward, or block | Block (simpler, matches "tell the student") / mask like Bedrock `ANONYMIZE` | Masking needs ordering care and changes what agents see |
| Add a local ONNX toxicity model as Stage 0.5 | No (recommended for now) / yes, after measuring CPU latency | New large pinned dependency |
| Shadow-mode period before enforcing | Length and review sample size | No published guidance exists |

## Conclusion

The question "how do I avoid running every check?" turns out to be the wrong worry for a chat gateway. Checks are cheap. What hurts is a check that fires without evidence. The production answer is to make every detector earn its finding: a trigger before it runs, a checksum or structure rule before it matches, a context word before it reaches high confidence, and a model with context before anything ambiguous is blocked. That reframes the Presidio failure as a design problem, not a tool problem. Many context-free recognizers voted, and the highest score won. It also reframes the workerd question. Once validators are generated offline and pinned, the main risk is wrong logic, not escape, so turning generated code into reviewed data plus a golden-set gate does more good than a stronger sandbox.

For the Hub specifically, the decisive advantage is position. Unlike the general gateways, it already parses every A2A part, knows which hop a message is on, and signs every caller. That lets it attach a small, explicit policy to each hop and report each decision as a real telemetry event. The next concrete step is to build the golden set and Stage 0 table first, because both are free to test. Then add the Haiku judge in shadow mode and let measured disagreement, not guesses, set the thresholds.
