# Hold the message, hide the judge

*Research synthesis, Friday, Oct 30, 2026 07:55 PM PDT. Built from the three note files in `research_notes/IDS speed methods for guardrails/`, plus the earlier report and notes on AI gateway guardrails. Each section separates **proven facts** (cited) from **interpretations** (my reasoning, labelled as such). Measurements that still have to be taken on this machine are collected in their own section near the end.*

Intrusion detection systems keep up with network speed in one of two ways, and neither of them makes the costly analysis fast. Signature engines (Snort, Suricata) do **cheap work on everything and costly work rarely**. They run one combined literal scan over each packet, and the expensive regex and rule checks run only for the few rules whose literal appeared. On top of that they enforce hard time caps (Snort's default is **500 µs per packet and per rule**) with an explicit choice of what happens when a cap is hit. AI-based network detection products mostly get their speed by **not being in the path at all**. Darktrace, Vectra and ExtraHop watch a copy of the traffic and react seconds later. The few products that do put machine learning inline (Palo Alto, Fortinet) **hold only the suspicious slice, under a time cap (Palo Alto's default is 200 ms), with an allow-or-block switch for when the cap runs out**. For the University Hub, that means the Haiku judge cannot be made fast. It can only be hidden or made rare. The pattern that transfers best is: run deterministic checks inline on every message (well under a millisecond in-process), start the judge **at the same moment as the Hub's own router call** so the two waits overlap, forward to the agent only after the judge passes, and hold outbound replies and professor posts the same way. A caveat changes the size of the problem: an independent benchmark lists Claude Haiku 5.5's time to first token at low effort as **about 7.9 s**, not the 1–2 s the owner assumed. The real latency of a short judge prompt on this project is unknown, and it is the first thing to measure. The Hub already logs `latencyMs` for every live model call, so that measurement is cheap.

## Signature engines stay fast by doing the costly work rarely

**Proven facts.** Snort 3 "evaluates rules in a two-step process which includes a fast pattern search and full evaluation of the signature." Rules are grouped by protocol, port and service, and each group is compiled into a multi-pattern search engine "designed to search for all patterns with just a single pass through a given packet or buffer" ([Snort 3 User Manual §2.7](https://snort.org/downloads/snortplus/snort_user.pdf)). Only one literal per rule, the **fast pattern**, goes into that combined scan. Full evaluation is "a fairly costly process which is why fast patterns are so important," and it "aborts on the first nonmatching option" ([Snort 3 User Manual §2.7.3](https://snort.org/downloads/snortplus/snort_user.pdf)). Suricata does the same. It picks the "strongest" content per rule, and its docs show a rule writer overriding the automatic choice because "'User-Agent:' will be a match very often" while "'Badness' appears less often" ([Suricata prefilter docs](https://docs.suricata.io/en/latest/rules/prefilter-keywords.html)). The Hyperscan paper explains why this works: multi-string matching beats multi-regex matching "by two orders of magnitude, and **most input traffic is innocent**, making it more efficient to defer a rigorous check." Choosing the literals automatically cut regex invocations "by over two orders of magnitude," and porting Snort to Hyperscan raised its single-thread throughput from **113 Mbps to 986 Mbps** ([Hyperscan, NSDI '19](https://www.usenix.org/system/files/nsdi19-wang-xiang.pdf)). The same paper records the failure mode: when the literals really are present, prefiltering can cost **more** than scanning naively.

The second trick is the time cap. Snort 3's `latency` module sets `packet.max_time` and `rule.max_time` to **500 µs** each. It can "fastpath" a packet that runs over (stop inspecting it), and it can suspend a rule after 5 timeouts for up to 30 seconds, raising an alert each time ([Snort 3 Reference](https://snort.org/downloads/snortplus/snort_reference.pdf)). Suricata names the choice openly. Its "exception policies" decide what happens under memory pressure or parser errors, and the `auto` setting means **drop in IPS (inline) mode and ignore in IDS (passive) mode**. Every triggered policy is logged in the flow record ([Suricata exception policies](https://docs.suricata.io/en/latest/configuration/exception-policies.html)). The third trick is deciding once per flow. A pass rule passes "the rest of the flow," and bypass can push that decision down into a kernel hash table or the network card, so later packets skip detection entirely ([Suricata: Ignoring traffic](https://docs.suricata.io/en/latest/performance/ignoring-traffic.html)). The fourth is parallelism: Suricata's `workers` mode keeps each flow on one thread and "generally… performs the best" ([Suricata runmodes](https://docs.suricata.io/en/latest/performance/runmodes.html)). Community and vendor figures put full-ruleset inspection at roughly **1 Gbps per core** ([Suricata forum](https://forum.suricata.io/t/suricata-ids-on-100gbps-link-via-af-packet-and-an-intel-e810-cqda2-with-ice-driver/4892); [Napatech](https://www.napatech.com/support/resources/solution-descriptions/4x-suricata-performance-increase-for-napatech/)).

Zeek takes a different path. It is passive. Its C++ core turns packets into "policy-neutral" events that "describe what has been seen, but not why, or whether it is significant," and scripts apply site policy afterwards ([Zeek architecture](https://docs.zeek.org/en/master/about/architecture.html)). Blocking happens later, through NetControl rules sent to switches and firewalls ([Zeek NetControl](https://docs.zeek.org/en/master/frameworks/netcontrol.html)).

**Interpretation.** In plain terms, a signature engine is fast because it asks a cheap question first ("is any suspicious word here at all?") and asks the expensive question only when the answer is yes. The scale is very different for the Hub. One core inspects about 125 MB of traffic per second, which is roughly 30,000 four-kilobyte messages per second. Students type a few messages a minute. **Raw scanning speed is not the Hub's problem. Tail latency is**: a regex that backtracks badly, or a model call that takes seconds. The fast-pattern idea still matters, but for a different reason. It keeps the costly second stage, and especially the model, rare where that is safe.

## AI-based detection is fast because the AI usually waits outside the path

**Proven facts.** Vectra's appliance docs say "out of band deployment is the only supported method of traffic capture. There is no inline mode" ([Vectra docs](https://docs.vectra.ai/deployment/ndr-physical-appliances/x-series/x47)). ExtraHop RevealX is "a completely passive solution" fed by a mirror port or tap ([ExtraHop datasheet](https://assets.extrahop.com/datasheets/ExtraHop-Reveal(x)-POC-datasheet.pdf)). Darktrace reads mirrored traffic and responds by sending spoofed TCP resets, and its own specification admits these often cannot cross stateful devices and do not work for UDP ([Darktrace spec v1.5.1](https://cdn.prod.website-files.com/626ff4d25aca2edf4325ff97/6984ac7573b5414b46acdb7c_Darktrace%20Offering%20Product%20Specification%20v1.5.1.pdf)). Cisco Secure Network Analytics works on flow summaries (NetFlow, IPFIX) rather than payloads ([Cisco SNA white paper](https://www.cisco.com/c/en/us/products/collateral/security/stealthwatch/white-paper-c11-740605.pdf)).

The inline products look different. Palo Alto's documentation says cloud inline analysis "can … introduce **100–200 milliseconds** of latency" ([PAN-OS 12.2](https://docs.paloaltonetworks.com/ngfw/new-features/by-version/panos/12-2)). It is governed by a **Max Latency** setting whose "default value is 200ms," and an "Allow on Max Latency" box. Unticking it "sets the NGFW action to block," and "Log Traffic Not Scanned" records what was skipped ([Configure Inline Cloud Analysis](https://docs.paloaltonetworks.com/advanced-threat-prevention/administration/configure-threat-prevention/configure-inline-cloud-analysis)). To cut the latency, Palo Alto moved the same models onto the firewall ("Local Deep Learning"), which runs "when content looks suspicious" and claims verdicts up to 100× faster than cloud-only (vendor claim) ([PAN-OS 11.2](https://docs.paloaltonetworks.com/pan-os/11-2/pan-os-release-notes/features-introduced-in-pan-os/content-inspection-features)). Fortinet allows known-good files, blocks known-bad ones, and **holds unknown files** in a sandbox until a verdict, for up to 50 seconds, with block, log or ignore on timeout ([FortiOS 7.2.1](https://docs.fortinet.com/document/fortigate/7.2.0/new-features/599740/inline-scanning-with-fortiguard-ai-based-sandbox-service-7-2-1)). Research systems that run machine learning at line rate do it by shrinking the model to fit the hardware: random forests in switches (pForest), **up to 221 ns** added latency on a switch chip (Taurus), and binary neural networks on network cards that stay under 40 µs where a CPU baseline climbed past 800 µs (N3IC) ([pForest](https://arxiv.org/abs/1909.05680); [Taurus](https://arxiv.org/pdf/2002.08987); [N3IC](https://www.usenix.org/system/files/nsdi22-paper-siracusano.pdf)).

Accuracy is the hidden cost. Axelsson's base-rate argument is that **false alarms, not missed attacks, limit intrusion detection**: when real attacks are rare, even a small false-alarm rate buries the real ones ([Axelsson, ACM TISSEC](https://dl.acm.org/doi/pdf/10.1145/357830.357849)). Arp et al. found at least three methodological pitfalls in every one of 30 top-venue security ML papers ([USENIX Security 2022](https://www.usenix.org/system/files/sec22summer_arp.pdf)). Text guards show the same collapse: CPU classifiers with F1 around 0.96 on familiar data fell to **0.11–0.42** on new jailbreak styles, and 72.2% of those attacks got confident "benign" scores ([Majhi et al., arXiv 2512.19011](https://arxiv.org/html/2512.19011)).

**Interpretation.** "AI-based and fast" usually means the AI watches from the side and accepts a few seconds of exposure. That model cannot meet the owner's inbound rule, because the message would already be at the agent. What the Hub can copy is the inline pattern: hold, run the model only where it is needed, cap the wait, and decide in configuration what happens at the cap. The lesson from the line-rate research is also useful. Speed came from **using a much smaller model**, not from making a big one faster. For text, the smaller model is a local classifier or a typed-decision model like Jev, and it pays for its speed in accuracy on unfamiliar phrasing.

## Which techniques transfer to the Hub, and which do not

**Interpretation (this table is my judgment, built on the cited facts above and in the earlier gateway report).** The deciding question for each technique is whether it depends on the network's huge scale or long flows, or whether it is really about the order and timing of checks.

| IDS technique | What it does, plainly | Transfers? | Hub form |
|---|---|---|---|
| Fast-pattern prefilter | One cheap word scan decides which costly checks run | **Yes** | Each detector has a trigger (a digit run, "ssn", a lexicon word). The Luhn check, SSN structure and keyword-window checks run only when their trigger fires |
| Hyperscan SIMD speed | Very fast multi-pattern matching in C | **No** | Plain V8 regexes are enough at 4 KB. The earlier report's local micro-benchmark measured about 15–80 µs for a dozen regexes (researchers' own run, unverified) |
| Streaming mode | Match patterns across packets | **No** | Messages arrive whole, and token streaming is out of scope |
| Hit-rate counters (`qualified_events`) | Count how often a trigger fires versus confirms | **Yes** | Per detector: triggered, confirmed, blocked. A trigger with a low confirm rate is a bad trigger |
| Hard time caps per packet and per rule | Stop waiting at a fixed limit | **Yes** | Per stage, per hop. Note: a synchronous regex cannot be timed out on Node's main thread (see below) |
| "Fastpath" (skip inspection on timeout) | Let it through unchecked when slow | **No for PII and inbound** | A skipped check must never mean a silent pass. It becomes an explicit, logged policy choice |
| Auto-suspend a slow rule | Turn off a rule that keeps timing out | **Partly** | Quarantine a slow validator *version* and go back to the last pinned one, with an alert. Never just drop the check |
| Exception policy (fail open or closed per mode) | A written decision for overload and errors | **Yes** | Per hop and per check, in config, and every use is logged as telemetry |
| Flow bypass / "trust the rest of the session" | Decide once, skip later packets | **No** | Every chat message is new content. Conversation state may only *raise* scrutiny |
| Reputation and blocklist lookups | Hash-table lookup of known-bad items | **Yes** | Exact-hash set of known-bad messages; verdict ledger keyed by message ID (see caching below) |
| Workers runmode, flow affinity | Keep a flow on one thread, in order | **Partly** | One conversation's checks stay in order (free on the event loop). Worker threads only to make a check killable |
| Zeek: neutral events, policy afterwards | Analyze after delivery, react later | **Outbound low-severity and audit only** | Post-delivery re-check, flags and staff alerts. Never for the inbound block decision |
| NDR out-of-band ML | Watch a copy, react in seconds | **No for blocking** | Useful only for audit and trends |
| Inline ML with hold plus cap (Palo Alto, Fortinet) | Hold only the uncertain slice, cap the wait | **Yes, core pattern** | Hold before forwarding, cap the judge, decide the timeout action per hop |
| Local model instead of cloud (Local Deep Learning) | Remove the network round trip | **Partly** | A local ONNX classifier is possible, but it is less accurate on new phrasing |
| Tiny in-network models (pForest, Taurus, N3IC) | Fit a small model to hardware | **Idea only** | "Use a smaller model for speed" is the lesson. The hardware is not relevant |
| Traffic sampling | Inspect only some packets | **No** | Cisco itself warns sampling hurts detection ([Cisco SNA 7.4.2](https://www.cisco.com/c/dam/en/us/td/docs/security/Analytics/7_4_2_Analytics_Detections_Alerts_Observations_DV_2_2.pdf)) |
| Base-rate lesson | False alarms dominate when attacks are rare | **Yes** | Set thresholds on false blocks measured on benign university chat, not on benchmark F1 |

Two items need a plain explanation. First, **Node cannot interrupt a running regex**. A synchronous check on the event loop blocks everything, and a `Promise.race` timer cannot fire until it finishes. So a time cap on deterministic checks only works if the patterns cannot backtrack badly (a linear-time engine such as `re2`, or patterns checked as ReDoS-safe, which this project already does for A2UI), or if the check runs in a separate process or worker that can be killed. That is the one speed-related argument *for* putting validators in workerd: it gives a boundary you can kill. Second, the **"decide once per flow" trick fails** for chat. In a network, the later packets of a judged flow are often more of the same. In chat, message two can contain the SSN that message one did not.

## A latency budget and pipeline for the Hub

**Proven facts this design rests on.** Running a guard in parallel with other work is standard. OpenAI's Agents SDK runs input guardrails "concurrently with the agent's execution" by default, and warns that "the agent may have already consumed tokens and executed tools before being cancelled." Its blocking mode guarantees "the agent never executes" ([OpenAI Agents SDK](https://openai.github.io/openai-agents-python/guardrails/)). LiteLLM's `during_call` runs the guard alongside the LLM call, and the "Response not returned until guardrail check completes" ([LiteLLM](https://docs.litellm.ai/docs/proxy/guardrails/quick_start)). NVIDIA states "There is no deployment-independent p50, p95, or throughput for a guardrails configuration" ([NeMo FAQ](https://docs.nvidia.com/nemo/guardrails/resources/runtime-security-faq)). Measured judge speeds: Claude Haiku 4.5 had a **median of 2,066 ms** as a guardrail, against **328 ms** for TypeSafe Jev. But Jev caught 78.2% of evasive prompts against Haiku's 94.0%, and wrongly flagged 9.6% of benign prompts against Haiku's 14.1% ([jev-as-a-guardrail](https://github.com/rahulbansalc6414/jev-as-a-guardrail)). A separate gateway benchmark measured Jev at 447 ms p50, catching 69.5% of unsafe prompts and blocking 9.7% of benign ones ([jev-guardrail-benchmark](https://github.com/randilt/jev-guardrail-benchmark)). Artificial Analysis lists Haiku 5.5's time to first token at low effort as **7.89 s**, with prompt length not stated ([Artificial Analysis](https://artificialanalysis.ai/models/claude-haiku-5-5-low)). A fine-tuned DistilBERT on native ONNX Runtime CPU ran at **5.66 ms p50** ([inference-lab](https://github.com/SaiArrow/inference-lab)). Nielsen's limits are 0.1 s (feels instant), 1 s (flow kept, delay noticed) and 10 s (attention lost without progress) ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)). In project code, `src/hub-agent.js` already emits `model_call_started` and `model_response_received` with `latencyMs` around the live router call, and `src/llm.js` already takes a `timeoutMs` per call with no retries.

**Interpretation (everything below is my design).** The budget is built so a clean message pays almost nothing extra beyond what the Hub already spends, and so every timeout has a written outcome.

### Inbound: student message to the Hub

The order matters more than the speed. Stage 0 runs first and alone, because it is nearly free and a definite block there saves a paid call. The judge and the router then start together, because both are work that stays inside the Hub. Nothing is forwarded until the judge says allow. This keeps the owner's rule strictly: the agent never sees a message the judge would block.

| Step | Runs | Target | Cap | At the cap or on error |
|---|---|---|---|---|
| 1. Stage 0 deterministic (SSN, cards, offensive lexicon, known-bad hashes) in-process, data-spec engine | Inline, every message | under 1 ms | 5 ms (only enforceable with ReDoS-safe patterns) | **Fail closed**: student told "we couldn't check your message; nothing was sent" |
| 1b. Same, if moved to workerd under gVisor | Inline | unmeasured | set after measuring (start at 50 ms) | Fail closed, and kill and restart the worker |
| 2. Verdict ledger lookup | Inline | under 0.1 ms | none | Miss means go on to step 3 |
| 3a. Haiku judge (one structured call, all categories, Stage 0 hints passed in) | **In parallel with 3b** | unknown, measure first | measured p99 plus margin (placeholder 6 s) | **Fail closed**, honest notice, the student may resend. Logged as `guardrail_timeout` |
| 3b. Router (Hub's existing call), registry and readiness checks, A2A request built | In parallel with 3a | existing | existing | Existing behaviour |
| 4. Forward to the specialist | Only after 3a says allow | — | — | — |

What the student feels: a Stage 0 block is answered in milliseconds. A clean message waits **max(judge, router)** before forwarding, instead of judge plus router. When the Hub runs the live Haiku router, the overlap hides about one model call. When the router is mock or direct, nothing is hidden and the full judge time is added. The UI should show an honest "Checking your message…" status driven by a real `guardrail_check_started` event, which fits the hop-by-hop strip and the project's rule that only real events mark steps.

I recommend **fail closed on judge timeout** for inbound because the owner's rule is strict and a hidden fallback is banned in this project. The cost is a visible "please resend" when the provider is slow. If the measured p99 makes that too frequent, there are three honest alternatives, each with a stated cost. (a) **Fail open with a post-delivery re-check**: let the call keep running past the release deadline, and if the late verdict says block, flag the conversation and alert staff. This breaks the strict reading of the rule, because the agent has already seen the message. (b) **A confident-safe fast lane**: very short messages that match the router's known capability examples, with no Stage 0 hints, skip the judge. This trades recall, and must be measured on a labelled set first. (c) **Jev as the inline judge, with Haiku only when Jev is unsure**: roughly 300–450 ms instead of seconds, but the cited data shows about 16 points lower recall on evasive phrasing. A fourth option, **folding the routing and safety verdict into one Haiku call**, saves a whole call. But it mixes two jobs in one prompt, so a prompt injection aimed at one could sway the other. I would test it only after the separate version works.

### Outbound: specialist reply to the student

Replies arrive whole, because there is no token streaming. So the Hub can hold a reply exactly as the inline firewalls hold a file. Stage 0 runs on every reply and **fails closed**: an SSN or card in an agent's answer is withheld, and the student is told a reply was held back and why. The judge then runs on the held reply. The student is already waiting several seconds for the agent, so the judge adds to a wait that is already noticed, not to an instant one. I recommend a **shorter cap here (placeholder 4 s) with fail open plus post-delivery re-check**. The reply comes from the university's own agents, which already run their own scope checks. If the late verdict says block, the Hub sends a visible "retracted" event, which the project's honest-state rules require to be a separate, real event. If the owner wants outbound to be as strict as inbound, the same fail-closed rule applies at the cost of more "reply held" notices.

### Professor posts

Posts land in an inbox, and the student cannot know when a post was written. A hold of several seconds is invisible. So posts get **Stage 0 plus the judge, fully held, fail closed, with a generous cap (30 s)**. A refused post goes back to the professor with the reason, and nothing is delivered. This is the one hop where the owner's latency worry does not apply at all.

### Caching

The safe cache is an **exact-match verdict ledger**. Its key is direction + policy version + SHA-256 of the normalized text + a digest of the recent turns the judge saw. Intent depends on context, so the same words in a different conversation must not reuse a verdict. The project already dedupes retries by `(contextId, messageId)` and `operationId`. A ledger keyed the same way gives the cache benefit for retries and reconciles, and it cannot collide. Exact repeats are otherwise rare in chat, so do not expect a big hit rate. **Do not cache by meaning (embedding similarity) as a "pass."** Research shows high cosine similarity does not mean the same verdict, and such caches can be poisoned ([arXiv 2609.35908](https://arxiv.org/html/2609.35908v1)). A "close to known-bad" index is acceptable only as a trigger that raises scrutiny, never as a reason to skip the judge. A policy change bumps the version and empties the cache automatically.

### Timing records

Copy Snort's counters. Every stage emits its timing and outcome as Hub telemetry: check names, tiers, verdict, `latencyMs`, and which policy fired at a cap. Never the text. This goes through the existing `redactTelemetry` allowlist. It turns tuning into reading numbers rather than guessing.

## Conclusion

The IDS world's real answer to "how do you inspect at line speed" is that **nobody runs the slow analysis inline on everything**. Signature engines make the slow part rare. NDR products move it out of the path. Inline firewalls hold only the uncertain slice and write down what happens when time runs out. The Hub has an advantage those systems lack. Its traffic is tiny, every message arrives whole, and it already spends its own model call (the router) on every message. So it can afford to run the judge on every message and hide most of the cost behind work it was doing anyway, without breaking the rule that blocked text never reaches an agent. The owner's worry is right in one way they may not expect. The risk is not the median judge time but its tail, and possibly a much higher baseline than assumed for Haiku 5.5.

The practical order of work follows from that. Measure the real judge latency first, using telemetry the project already has. Build the deterministic Stage 0 as data run by a trusted engine, with ReDoS-safe patterns so its cap means something. Wire the judge in parallel with the router, fail closed inbound, and run it in shadow mode. Then let the measured p99 and false-block rate decide whether a faster first judge (Jev or a local classifier) is worth the recall it costs. That last choice is a trade the owner should make with numbers, not one the architecture should make silently.
